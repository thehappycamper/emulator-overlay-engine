# P01-T004: Implement Safe Declarative Mapping Contract

- **Task ID:** `P01-T004`
- **Phase:** `P01` — Platform Mapping Foundation (see [implementation plan](../../project/implementation-plan.md))
- **Status:** completed (one follow-up finding open as `P01-T007`)
- **Owner:** thehappycamper (with coding-agent assistance)

## Objective

Introduce a domain-neutral `mapping.schema.json`, a pure/whitelisted JSON expression AST evaluator with no `eval`/`Function`/dynamic-import/host-global access, an executable mapping pipeline, and automated schema validation — replacing the earlier JavaScript-string-like calculated-field example with a safe structural format.

## Why This Task Exists

This closed the highest-priority finding from an independent architecture-readiness audit of the repository: `examples/mapping-project/mapping.example.json` represented calculated fields as JS-like strings (e.g. `[primary_type, secondary_type].filter(Boolean)`), and no `mapping.schema.json` existed at all. Recorded in `docs/decisions/0012-safe-mapping-expressions.md`.

## Dependencies

`P01-T001`/`P01-T002` (extension/template schemas — mapping's target descriptor and template-type reuse build on them).

## Security/Compatibility Considerations

This task's entire purpose is a security boundary: untrusted, community-authored mapping projects must not become an arbitrary-code-execution path. See Review Findings for the adversarial review outcome.

## Review Findings

An adversarial security review of this commit (independent agent review, same day) checked prototype pollution, host-global escape, arbitrary method invocation, divide/modulo edge cases, coercion, JSON Pointer decoding, and denial-of-service vectors. Findings:

- **Confirmed safe:** no `eval`/`Function`/dynamic import/host-global access anywhere in the evaluator; `__proto__`/`constructor`/`prototype` path segments blocked at the one real assignment vector (`parseJsonPointer`, used by both read and write paths) and empirically verified (writing to `/__proto__/polluted` throws; `{}.polluted` stays `undefined` afterward); `Object.fromEntries`/`JSON.parse` used everywhere instead of raw bracket assignment with attacker-controlled keys; finite-number and strict-type checks correctly reject `NaN`/`Infinity`/JS coercion surprises; expression nesting bounded at depth 100; no partial mutation observable on a failed mapping (the `target` object is discarded, never returned, if an error is thrown mid-application).
- **P1 blocking finding (opened as `P01-T007`):** `src/mapping/apply.js`'s `setJsonPointer` places no upper bound on numeric array-index path segments. Empirically reproduced: a `targetPath` of `/arr/4000000000/y` (19 characters) instantly creates a JS array with `.length === 4000000001`; at a smaller, safely-testable scale (`/arr/10000000/y`), `JSON.stringify` of the resulting object alone took ~900ms and produced a 50MB string from a one-field source object. This is a genuine amplification DoS (tiny input, unbounded output), not a theoretical one, and directly undercuts the "safe to load from untrusted community data" claim for this input class. Recommended fix: bound array-index writes to `0 <= index <= currentArray.length` (RFC 6902 JSON Patch "add" semantics). Does not require touching the schema or the expression AST.
- **Non-blocking:** `and`/`or` do not short-circuit (unlike `if`, which correctly evaluates only the selected branch) — a documentation/consistency gap, not a security issue. `docs/knowledge/adapter-contracts.md` was not updated in this commit despite `architecture.md`/`README.md` inserting a new "Mapping Runtime" pipeline stage, creating a temporary doc inconsistency — closed by `P01-T006`.

Overall verdict: **APPROVE WITH FIXES** — architecture/contract design sound, no redesign needed; one focused fix commit required before the mapping runtime should be considered safe for untrusted input (tracked as `P01-T007`).
