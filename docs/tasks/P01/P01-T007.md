# P01-T007: Harden JSON Pointer Array Writes

- **Task ID:** `P01-T007`
- **Phase:** `P01` — Platform Mapping Foundation (see [implementation plan](../../project/implementation-plan.md))
- **Status:** review — implemented on a parallel branch, not yet merged to `main`
- **Owner:** Codex (branch `fix/mapping-array-hardening` — **not implemented on this branch**)

## Objective

Close the sparse-array amplification denial-of-service found during adversarial security review of `P01-T004` (commit `13e926262b1685ccbcf232e834b6660a92485e4e`). Bound numeric array-index segments in `setJsonPointer` (`src/mapping/apply.js`) so a mapping project's `targetPath` cannot create arbitrarily large sparse arrays from a short input string.

## Why This Task Exists

`P01-T004`'s stated purpose is that mapping projects are safe to load from untrusted, community-authored data. Review found that claim did not hold for one input class: `setJsonPointer` places no upper bound on a numeric array-index path segment. A `targetPath` of `/arr/4000000000/y` (19 characters) instantly produces a JS array with `.length === 4000000001`. At a smaller, safely-testable scale (`/arr/10000000/y`), `JSON.stringify` of the resulting object alone took ~900ms and produced a 50MB string from a source object containing a single field — confirming this is a real amplification attack (tiny input, unbounded downstream cost via `JSON.stringify`, Ajv `items` validation, or array iteration), not a theoretical one. Full write-up: `P01-T004`'s Review Findings section.

## Acceptance Criteria

- Writing through a numeric array-index path segment that is out of bounds (i.e. not `0 <= index <= currentArray.length`, following RFC 6902 JSON Patch "add" semantics: sequential append or in-bounds replace only) throws instead of silently succeeding.
- All existing tests continue to pass (39/39 as of `P01-T004`).
- A new regression test exists asserting the large-index case throws (e.g. `targetPath: "/arr/999999999/x"`).

## Implementation Notes

Observed on branch `fix/mapping-array-hardening` (pushed to `origin/fix/mapping-array-hardening`), commit `c40dd430cc1a5f5904ba3c90a888341cf29c14fd` "Harden mapping array writes," authored 2026-08-08. This governance branch does not include that commit — noted here only because both branches share this working directory and the commit is visible in local git history.

The fix matches the recommended approach exactly: a new `resolveArrayIndex(array, segment)` helper rejects non-array-index segments, non-safe-integer indices, and any index `> array.length` (`RangeError`, message includes `"exceeds current length"`), and rejects an in-bounds index that doesn't reference an existing element (sparse-gap guard). A new `assignContainerValue` helper routes array writes through `push` (when index equals current length) or in-place replacement (when index is a valid existing element), instead of raw bracket assignment. This is applied both to the final-segment write and to intermediate container traversal in `setJsonPointer`.

Also included in that commit (beyond this task's original scope, but consistent with it): a `docs/knowledge/extension-workbench.md` note that `compact` follows `filter(Boolean)` truthiness (removes `0`/`false`/`""` along with null/missing) — closing the non-blocking `compact`-truthiness documentation gap noted in `P01-T004`'s Review Findings. And a `docs/knowledge/adapter-contracts.md` wording pass (pipeline label changed to `Source Provider / Adapter -> Source Contract -> Mapping Runtime -> Named Target`; clarified when an adapter may bypass mapping to emit a target directly) — outside this task's original scope but touching the same file `P01-T006` last edited.
