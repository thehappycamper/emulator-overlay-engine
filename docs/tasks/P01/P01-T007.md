# P01-T007: Harden JSON Pointer Array Writes

- **Task ID:** `P01-T007`
- **Phase:** `P01` — Platform Mapping Foundation (see [implementation plan](../../project/implementation-plan.md))
- **Status:** completed

## Objective

Close the sparse-array amplification denial-of-service found during adversarial security review of `P01-T004` (commit `13e926262b1685ccbcf232e834b6660a92485e4e`). Bound numeric array-index segments in `setJsonPointer` (`src/mapping/apply.js`) so a mapping project's `targetPath` cannot create arbitrarily large sparse arrays from a short input string.

## Why This Task Exists

`P01-T004`'s stated purpose is that mapping projects are safe to load from untrusted, community-authored data. Review found that claim did not hold for one input class: `setJsonPointer` places no upper bound on a numeric array-index path segment. A `targetPath` of `/arr/4000000000/y` (19 characters) instantly produces a JS array with `.length === 4000000001`. At a smaller, safely-testable scale (`/arr/10000000/y`), `JSON.stringify` of the resulting object alone took ~900ms and produced a 50MB string from a source object containing a single field — confirming this is a real amplification attack (tiny input, unbounded downstream cost via `JSON.stringify`, Ajv `items` validation, or array iteration), not a theoretical one. Full write-up: `P01-T004`'s Review Findings section.

## Acceptance Criteria

- Writing through a numeric array-index path segment that is out of bounds (i.e. not `0 <= index <= currentArray.length`, following RFC 6902 JSON Patch "add" semantics: sequential append or in-bounds replace only) throws instead of silently succeeding.
- All existing tests continue to pass (39/39 as of `P01-T004`).
- A new regression test exists asserting the large-index case throws (e.g. `targetPath: "/arr/999999999/x"`).
- Normal dense writes, existing-element traversal/replacement, and append-at-length continue to work.
- Prototype-sensitive path protections remain intact.
- Sequential calculated fields can read target values produced by earlier calculated fields.

## Implementation Notes

Implemented originally at `c40dd430cc1a5f5904ba3c90a888341cf29c14fd`. The dedicated task worktree rebased the branch onto governed `origin/main` at `f5f6e2b67b07197d531bf9055f82150a8ab0fd9b` without conflicts. `git range-diff` reported the implementation patch unchanged; the rebased implementation commit is `14a66f1`.

The fix matches the recommended approach exactly: a new `resolveArrayIndex(array, segment)` helper rejects non-array-index segments, non-safe-integer indices, and any index `> array.length` (`RangeError`, message includes `"exceeds current length"`), and rejects an in-bounds index that doesn't reference an existing element (sparse-gap guard). A new `assignContainerValue` helper routes array writes through `push` (when index equals current length) or in-place replacement (when index is a valid existing element), instead of raw bracket assignment. This is applied both to the final-segment write and to intermediate container traversal in `setJsonPointer`.

Also included: a `docs/knowledge/extension-workbench.md` note that `compact` follows `filter(Boolean)` truthiness (removes `0`/`false`/`""` along with null/missing), and a `docs/knowledge/adapter-contracts.md` correction to `Source Provider / Adapter -> Source Contract -> Mapping Runtime -> Named Target`. The adapter document clarifies that a deterministic, documented, target-validated adapter may emit an already-normalized named target directly; downstream consumers still depend on the named target contract.

## Security/Compatibility Considerations

This task exists entirely because of a security finding. See Why This Task Exists. No compatibility concern — bounding array indices only rejects inputs that were already pathological; no legitimate mapping project should rely on sparse, far-out-of-bounds array indices.

## Review Findings

Claude's independent review of `P01-T004` returned "APPROVE WITH FIXES" and documented this as the blocking P1 finding. Claude's independent review of this fix branch (`fix/mapping-array-hardening` at `f1cc577`, in an isolated clone, no files modified) returned **verdict: APPROVE**, with no blocking findings. Summary of that review:

- Traced `resolveArrayIndex`/`assignContainerValue` in `src/mapping/apply.js` and confirmed the fix implements RFC 6902 "add" semantics exactly as recommended: rejects `index > array.length` (gaps/huge indices), rejects `index < array.length` with no existing element (pre-existing holes), and only permits append (`index === length`) or in-place replacement of an existing element.
- Independently reproduced both `/arr/4000000000/y` and `/arr/999999999/x` from a fresh script (not the branch's test file): both threw `RangeError` immediately (0–1ms), with the target array's length remaining `0` — confirming no amplification, even transiently.
- Ran an independent regression script beyond the branch's own tests: sequential append building a dense array, deep nested array-of-array-of-object creation, non-numeric/negative/leading-zero index rejection, and plain nested object writes — all correct.
- Confirmed prototype-pollution defenses are untouched (the `__proto__`/`constructor`/`prototype` blocklist in `parseJsonPointer` runs before any segment reaches the new array-handling code, so no new bypass route exists) and independently verified `/__proto__/polluted` still throws.
- Confirmed the branch's own new test (`calculated fields can read target values from earlier calculated fields`) accurately documents real, correct `applyCalculatedFields` behavior — not a hopeful assertion.
- Confirmed governance records (this file, `implementation-plan.md`, `last-worked-on.md` as they stood pre-merge) accurately reflected implementation state, with no premature `completed`/merge claims.

Two non-blocking observations noted, neither requiring a fix: the pre-existing-hole guard isn't reachable through any current construction path in this codebase (defense-in-depth for future code, not closing a currently-exploitable gap); the isolation-worktree naming (`../EOE-P01-T007`) differs stylistically from `AGENTS.md`'s example convention, which is explicitly non-binding.
