## Implementation Notes

**Branch-collision incident (first increment):** partway through the first increment, `git status` unexpectedly showed `HEAD` on `fix/mapping-array-hardening` instead of `chore/project-governance-brand-agnostic`. `git reflog` showed a concurrent agent had checked out `main`, then `fix/mapping-array-hardening`, and committed `c40dd43` there, while this task's uncommitted edits (which didn't overlap any file `c40dd43` touched) rode along on top of the branch switch. Recovery: verified the uncommitted diff was exactly this task's own changes (`git diff --stat HEAD`), confirmed zero file overlap with `c40dd43`'s changed files, then `git checkout chore/project-governance-brand-agnostic` to carry the uncommitted work back to the correct branch cleanly. No work was lost, but this is exactly the failure mode the second increment's Concurrent Agents rule exists to prevent — the recovery worked this time because the file sets happened not to overlap; that is luck, not a guarantee.

**Isolation approach for the second increment:** `git worktree add` for the same branch that was already checked out in the primary directory fails (`fatal: '<branch>' is already used by worktree at '<path>'`) — a branch can only be checked out in one worktree of a given repository at a time. Since the primary checkout already legitimately had `chore/project-governance-brand-agnostic` checked out, the correct isolation move was an independent `git clone` from `origin` (not a worktree of the local repo, and not a plain re-checkout in the shared directory), which has no shared-state dependency on the primary checkout at all. This is documented in `AGENTS.md`'s Concurrent Agents section as the fallback when the worktree path is blocked by this constraint.
