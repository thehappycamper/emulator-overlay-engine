## Objective

Introduce the minimum real Pokemon domain package and a domain-neutral resolution boundary. Preserve the existing MVP while proving that shared platform code can remain domain-neutral and Pokemon calculators can be migrated incrementally.

## Why This Task Exists

ADR 0008 established a domain-neutral core with Pokemon as the first domain, but the implemented type chart, damage, projection, and capture logic still lived under the generic-looking `src/engine/` path. P02 needs a concrete, testable dependency direction before further Pokemon schema or UI migration:

```text
Platform Core
      |
Domain Registry / Boundary
      |
Pokemon Domain
```

This task proves that first boundary without attempting the full P02 phase migration.

## Architecture Introduced

`src/platform/domain-registry.js` provides a generic registry factory. It validates package objects and IDs, rejects duplicate IDs, and exposes immutable `has` and `resolve` operations. It imports no domain implementation.

`src/domains/index.js` is the application composition root. It explicitly supplies `pokemonDomain` to the generic registry and exports `resolveDomain`. Pokemon registration belongs here rather than in shared platform code.

`src/domains/pokemon/index.js` is the first domain descriptor and public calculator surface. It exposes stable ID `pokemon` and a frozen calculator collection backed by Pokemon-owned capture, damage/projection, and type-chart modules.

The current overlay resolves `pokemon` through the composition root. Legacy `src/engine/{capture,damage,type-chart}.js` paths re-export the package functions during incremental migration.

## Security/Compatibility Considerations

## Review Findings

Claude's independent review of this branch (`feat/P02-T001-pokemon-domain-boundary` at `2617f4a`, in an isolated clone, no files modified) returned **verdict: APPROVE WITH FIXES** (the "fixes" being a non-blocking, explicitly deferred follow-up — not a merge blocker). Summary:

- Confirmed `src/platform/domain-registry.js` contains zero Pokemon references and zero imports; the literal `"pokemon"` ID appears only in the composition root (`src/domains/index.js`) and the domain's own self-declaration (`src/domains/pokemon/index.js`), never in platform code — the composition-vs-platform-implementation distinction is drawn correctly.
- Confirmed dependency direction has no cycles: platform has no outgoing imports, the Pokemon domain package imports only its own siblings (never platform), and only the composition root imports both.
- Confirmed `src/domains/pokemon/{damage,capture,type-chart}.js` are byte-identical to their prior `src/engine/` versions — a pure move, no smuggled behavior changes.
- Independently ran `npm test` (51/51), plus an independent regression/exercise script beyond the branch's own tests: duplicate-domain-ID rejection, registry tamper resistance, frozen descriptor/calculator objects, stable object identity across repeated `resolveDomain` calls, and live end-to-end calculator resolution.
- **Non-blocking finding:** `createDomainRegistry` does not itself enforce immutability on the domain descriptors it's given — it freezes only its own `has`/`resolve` interface, not the domain objects passed in. Verified by registering an unfrozen test domain and mutating a calculator on it post-registration; `resolve()` returned the mutated version. Harmless today (the only registered domain, `pokemonDomain`, self-freezes; no dynamic/untrusted domain loading exists yet), but should be closed before a second domain or any dynamic loading is introduced, so immutability is a platform guarantee rather than a per-domain convention. Explicitly deferred to `P02-T003` rather than blocking this merge, per merge approval.
- Confirmed scope was correctly sized (narrow, well-bounded, honest about what's deferred) and governance records (this file, `implementation-plan.md`, `last-worked-on.md` as they stood pre-merge) accurately reflected implementation state with no premature completion claims.
