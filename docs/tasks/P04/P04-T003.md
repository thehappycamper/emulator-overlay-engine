## Objective

Integrate the existing `overlay.notification` action provider with a real local delivery path so a semantic event can produce a visible notification in the browser overlay, completing `event -> rule -> action request -> capability-gated executor -> overlay.notification -> local overlay delivery -> browser UI` without bypassing the executor or weakening any capability/authorization/replay guarantee `P04-T002` established.

## Why This Task Exists

`P04-T002`'s own recommended follow-up: "a real overlay-integration provider (wiring `overlay.notification` to the actual browser overlay) once the presentation layer exposes a suitable local delivery channel - still local-only, no network/webhook work implied." See [ADR 0029](../../decisions/0029-overlay-notification-local-delivery.md).

## Dependencies

`P04-T002` (capability-gated action executor, `overlay.notification`/`system.log` providers) complete and merged on `origin/main`.

## Scope

- `src/overlay/notification-feed.js` (new): pure, in-memory, TTL-pruned, capped notification feed store.
- `src/overlay/write-notification-feed.js` (new): atomic writer for `public/notifications.json`.
- `src/overlay/notification-view.js` (new): pure client-side reconciliation (`planNotificationRender`) deciding what's newly visible vs. expired.
- `src/overlay/notification-dom.js` (new): DOM node builder (`textContent`-only) and a polling panel controller (`createNotificationPanel`) reusing `createLiveStateController`.
- `src/overlay/app.js` (extended): wires a second, independent poll loop for notifications, rendered into a sibling container that never replaces the dashboard.
- `src/actions/providers/overlay-notification.js` (extended): optional `severity` field, `execute()` is now `async`, real sink failures propagate.
- `src/actions/providers/schemas/overlay-notification-payload.schema.json` (extended): optional `severity` enum, default `info`.
- `tools/emerald-live-state.mjs` (extended): real wiring - derives events from consecutive mapped states, evaluates the declarative rule, executes resulting requests through a capability-gated executor granted only `overlay.notify`, delivers to the real notification feed. Gained a proper ESM main-module guard and exported, independently-testable functions.
- `public/index.html`, `public/styles.css` (extended): notification container/config attribute, modest toast styling.
- `.gitignore` (extended): `notifications.json` (runtime-generated, like `live-state.json`).

## Non-Goals

Webhooks, external network integrations, emulator writes/input/savestates, multiplayer, hosted/cloud notification delivery, a general-purpose message bus, a new overlay/visual designer. Does not duplicate `P05-T012`'s session orchestrator - `tools/proof-emerald-bizhawk.mjs` needed zero changes.

## Acceptance Criteria

- A real `pokemon.fainted` event, through the real declarative rule at `examples/rules/pokemon-fainted-notification.rule.json`, produces a validated `overlay.notification` action request that the real executor executes, publishing to a real local notification feed.
- The executor's capability grant (`overlay.notify`) and per-request authorization (`sessionAuthorized`) still gate every notification exactly as `P04-T002` defined; no bypass path exists from rules/event detectors directly into overlay delivery.
- A replayed/duplicate action request never publishes a second notification.
- A notification delivery failure becomes a structured `EXECUTION_FAILED` result, never a thrown/unhandled error, and never stops the rest of a batch.
- The browser can receive and display a notification without replacing the dashboard, without duplicate-rendering an already-shown notification, with deterministic expiry (or explicit dismissal), and with no HTML/script injection possible from notification text.
- The browser overlay continues operating normally (dashboard polling unaffected) when the notification feed is absent, empty, or malformed.
- No notification/action-execution module can mutate normalized Pokemon state; the two local delivery paths (`public/live-state.json`, `public/notifications.json`) are structurally disjoint.

## Implementation Notes

**Two independent local file/poll channels, not one shared with `public/live-state.json`.** Coupling notification delivery into the normalized-state document (even via its `extensions` namespace) would tie a transient, platform-level UI concern to the domain-owned game-state contract's own change-detection cycle - a new notification would force a full dashboard re-render, which is exactly the "replacing the dashboard" outcome ruled out by requirement. `public/notifications.json` is a second, small, independently-polled file, served by the same unmodified static file server. See [ADR 0029](../../decisions/0029-overlay-notification-local-delivery.md) for the full reasoning.

**The feed store is pure and TTL-bounded, not a countdown.** `createNotificationFeed({ ttlMs, maxEntries, now })` assigns each published entry a fixed `deliveredAt` timestamp and prunes anything older than `ttlMs` before every read/write - the browser never has to track a shrinking "time remaining," it just reconciles to whatever the feed currently contains. `maxEntries` additionally bounds memory/output size regardless of TTL.

**Client-side reconciliation, not a client-side expiry timer.** `planNotificationRender(feedEntries, { renderedIds, dismissedIds })` is a pure function: given the latest poll's feed and what this browser session has already shown/dismissed, it returns exactly which entries are newly visible and which previously-shown ones fell out of the feed (expired server-side) and must be removed. This makes expiry deterministic (bounded by the feed's own TTL plus one poll interval) without any client-side `setTimeout` racing the server's own pruning clock.

**Textual safety is structural, not a convention.** Every notification DOM node (`buildNotificationNode`) is built with `document.createElement` + `.textContent` assignments only - never `innerHTML`, never string interpolation into markup. A message containing `<img src=x onerror=...><script>...</script>` renders as literal, inert text; this was verified against a real Chrome tab (see Implementation results), not just asserted by a unit test.

**Dismissal is independent of expiry.** A dismissed notification's id is tracked separately from "already rendered" ids, for the life of the browser session, so it is never re-shown even if the server has not pruned it yet by the next poll - verified live in the browser smoke (see below), including that it survives across multiple subsequent polls.

**Replay/duplicate protection needed no new mechanism.** `P04-T002`'s executor already guarantees a genuine replay never re-invokes `execute()`; since the real `notify` sink only runs inside `execute()`, a duplicate action request structurally cannot publish a second feed entry. No new dedup logic was added to the feed store for this - proven by a dedicated integration test using the real executor, real provider, and real feed together (not fakes).

**`overlay.notification`'s `execute()` is now `async`.** This is the one behavioral change to the provider itself: `await notify(payload.message, severity)` lets a real sink's file I/O genuinely propagate a rejection to the executor's own try/catch, becoming a structured `EXECUTION_FAILED` result. The payload contract gained one optional field, `severity` (`info`/`warn`/`error`, default `info`), mirroring `system.log`'s existing `level` field exactly - the smallest useful addition, not a new notification framework.

**All real wiring lives in `tools/emerald-live-state.mjs`**, the one place already established as allowed to import a Pokemon domain module for its own composition (mirroring `tools/proof-emerald-bizhawk.mjs`'s BizHawk-specific composition). `src/events`, `src/rules`, and `src/actions` remain completely domain-neutral - unmodified except for `overlay-notification.js`'s own payload/async change. `createEmeraldLiveStateSession(...)` builds one session's rules/feed/executor/event-sequencer, reused across every poll so event sequencing and replay tracking stay meaningful for the life of the session (not reset every 250ms); `processEmeraldEvents(...)` is the pure derive-events-then-evaluate-then-execute step, independently testable. The script previously had no ESM main-module guard at all (it ran its entire polling loop at module-load time) - this task added the same proven-correct `pathToFileURL(process.argv[1]).href === import.meta.url` guard already used elsewhere in this project, which was required to make the new logic importable by tests without side effects. `tools/proof-emerald-bizhawk.mjs` required zero changes: it already spawns `emerald-live-state.mjs` as a child process and matches its readiness log line unchanged, so the new event/rule/notification behavior is automatically part of the existing single-command proof session.

**Real browser smoke (see Implementation results below) confirmed, against an actual Chrome tab:** three notifications (info/warn/error) render in publish order with correct severity styling; a message containing `<img onerror=...><script>...</script>` renders as inert literal text with no dialog/script execution; clicking dismiss removes a notification and it never reappears across multiple subsequent polls even though the feed file still contained it; removing an entry from the feed file (simulating server-side TTL expiry) removes the corresponding DOM node within one poll interval. A genuinely live BizHawk/mGBA operator smoke was not performed in this environment (no emulator session available here); the fixture-driven CLI smoke below exercises the identical production code path a live session would use.

**A pre-existing, unrelated bug was found and is explicitly out of scope.** Loading the real `public/index.html`/`src/overlay/app.js` directly in a browser (no bundler) fails with `Failed to resolve module specifier "ajv/dist/2020.js"`, because `src/domains/pokemon/index.js` transitively imports `src/events/validate.js` (added in `P03-T001`), which imports the bare npm specifier `ajv/dist/2020.js` - something only a bundler or import map can resolve, and this project has neither. Confirmed present, byte-identical, on `origin/main` before this task's changes - not introduced here. The browser-side smoke above worked around it with a small temporary, uncommitted, deleted-after-use test harness page that imports only `notification-dom.js` (which has no `ajv` dependency), so this task's own deliverables were still genuinely verified in a real browser despite the pre-existing blocker. Fixing the dev-server/bundling gap itself is a separate, unrelated concern - flagged as a follow-up.

**Fix round: transactional (commit-after-success) publication (see [ADR 0029](../../decisions/0029-overlay-notification-local-delivery.md)'s addendum for full rationale).** Pre-merge scrutiny found a blocking gap: the original `createNotificationDelivery` mutated the in-memory feed (`feed.publish(...)`) *before* attempting the durable write. A write failure then left a notification committed in memory despite the action correctly reporting failure, and because P04-T002 never caches a non-`"executed"` outcome, a retry would publish a *second* entry on top of the still-present failed one; a slow, delayed write could also overwrite a faster, newer write's complete data with its own stale snapshot (a genuine, reproduced file-persistence race). Fixed with commit-after-success: `notification-feed.js` gained `prepare()` (computes the exact next feed state - same id/timestamp/pruning/cap logic as `publish()` - without mutating anything) and `commit(candidate)` (applies a previously-prepared candidate). `createNotificationDelivery` now does prepare → durably write → commit-only-on-success, so a failed write leaves the feed byte-for-byte as it was, and a retry's own `prepare()` starts from that exact same state (even reusing the same id). A small, local, bounded serialization queue inside `createNotificationDelivery` itself (not a general-purpose locking subsystem, and not a second replay mechanism) additionally guarantees two `notify()` calls through the same delivery instance can never both prepare from the same pre-write state and commit out of order - closing the theoretical race even though the real production path (P04-T002's sequential `executeAll()`, itself only ever driven by one fully-awaited `mapAndNotify()` call per poll) already serializes every real call. Verified against the pre-fix code directly: reverting only `createNotificationDelivery` reproduced all four regressions (surviving in-memory entry after a failed write, `[A, A]` on retry, a pre-existing entry incorrectly joined by a failed attempt, and the file-persistence torn-write race); re-applying the fix restored all four to green.

## Security/Compatibility Considerations

No new network surface: delivery is a local file written by the same process already writing `public/live-state.json`, served by the same unmodified static file server. No arbitrary-code-execution path: the browser-side renderer never evaluates or interprets notification text as markup (`textContent` only, structurally, not by convention) - verified against a real browser with an active XSS-style payload. A notification cannot mutate normalized Pokemon state: the notification feed and the live-state writer are separate modules writing separate files, with a dedicated regression proving this. Capability/authorization gating is unchanged and unweakened - a notification still requires both the `overlay.notify` capability grant and per-request `sessionAuthorized` context, exactly as `P04-T002` defined; this task adds no new bypass. `public/notifications.json` is a runtime-generated artifact (gitignored), never committed.

## Review Findings

Pre-merge review found one blocking issue, fixed on this same branch (see [ADR 0029](../../decisions/0029-overlay-notification-local-delivery.md)'s addendum and the fix-round Implementation Notes/Tests entries above for full detail):

1. Publication was not atomic from the action executor's perspective: `feed.publish()` mutated the in-memory feed before the durable write was attempted, so a write failure left a notification committed in memory despite the action reporting failure, and a retry could publish a duplicate; a delayed failed-then-retried write could also overwrite a newer successful write's file contents. Fixed with a commit-after-success design (`prepare()`/`commit()` two-phase publish plus a small local serialization queue).
