## Objective

Define the first capability-gated action execution boundary on top of merged `P04-T001`: a small, domain-neutral action-provider/executor interface that turns a validated `ActionRequest` into a real (but harmless) local effect, or a structured, fail-closed rejection - without ever letting rule evaluation itself perform a side effect.

## Why This Task Exists

`P04-T001`'s own recommended follow-up: "define a capability-gated action-provider boundary and a minimal in-memory executor for approved local actions. Keep provider mutation and permissions outside rule evaluation." See [ADR 0027](../../decisions/0027-capability-gated-action-executor.md).

## Dependencies

`P04-T001` (declarative rules producing validated action requests) complete and merged on `origin/main`.

## Scope

- New domain-neutral `src/actions/execute.js`: `createActionExecutor(providers, options)`, a four-stage fail-closed pipeline (supported → capability-granted → authorized → payload-valid → execute), returning a schema-validated `ActionResult` for every outcome, never throwing for request-shaped input.
- New `src/actions/schemas/action-result.schema.json` and `assertValidActionResult`/`ActionResultValidationError` added to `src/actions/validate.js`.
- Two harmless local action providers proving the architecture: `src/actions/providers/overlay-notification.js` (`overlay.notification`) and `src/actions/providers/system-log.js` (`system.log`), each with its own JSON Schema-validated payload contract and an injectable execution sink (defaults to a console line - no real I/O).
- Explicit, tested replay/duplicate-request semantics.

## Non-Goals

Memory writes, input injection, savestate operations, webhooks, Discord/Twitch/OBS integrations, scripting, multiplayer, or provider-specific emulator actions. `src/rules/evaluate.js` is not modified - rule evaluation remains completely side-effect-free and does not import this module.

## Acceptance Criteria

- A supported, capability-granted, authorized action with a valid payload executes and returns a schema-valid, `"executed"` result.
- An unsupported action type, a missing capability, an unauthorized action, and a malformed payload each fail closed with a distinct structured code, never executing the provider.
- A provider exception (sync or async) is returned as a structured `"failed"` result, never thrown from the executor.
- `executeAll()` processes a batch of requests strictly in array order (never concurrently).
- Duplicate/replayed action handling is explicitly defined and tested: an identical replay is not re-executed; a different request that happens to share the same idempotency key is never conflated with a cached result.
- The source `ActionRequest` is never mutated.
- Rule evaluation and action execution remain in separate modules with no import coupling in either direction.

## Implementation Notes

**Four-stage fail-closed pipeline.** Every `execute()` call passes through, in order: request-schema validity → provider registered for `actionType` (`UNSUPPORTED_ACTION_TYPE`) → `requiredCapability` present in the executor's granted-capability set (`MISSING_CAPABILITY`) → the provider's own `authorize(payload, context)` hook, if present (`UNAUTHORIZED_ACTION`) → the provider's own `validatePayload(payload)` (`INVALID_PAYLOAD`) → `execute(payload, context)`, wrapped in try/catch (`EXECUTION_FAILED` on throw). Every stage returns a fully schema-validated `ActionResult` rather than throwing, so a caller looping over many requests is never crashed by one of them.

**Capability decoupled from action type.** A provider declares `requiredCapability` as its own string, not required to equal `actionType`. The two proof providers happen to use similarly-named capabilities (`overlay.notify`, `system.log`), but the mechanism itself is capability-based, not action-type-based - independently verified by a test granting only one of the two capabilities and confirming the other provider's action is rejected `MISSING_CAPABILITY` even though its provider is registered. This is the seam a future, stronger-gated action (e.g. an emulator-write capability that is normally never granted) plugs into without any change to the executor framework or the rule engine.

**Authorization is a second, dynamic gate, deliberately distinct from the static capability grant.** Both proof providers require `context.sessionAuthorized === true` in their `authorize()` hook - a simple, uniform "this execution context may run local harmless actions" signal, independent of whether the executor was constructed with the underlying capability at all. A provider whose `authorize()` throws is treated as an authorization failure (`UNAUTHORIZED_ACTION`), not a crash.

**Replay/duplicate semantics, explicit by design.** Requests are keyed by `` `${correlationId}:${sequence}` `` - `action-request.schema.json` already documents `sequence` as unique within one evaluation run, so this is the smallest honest identity without inventing a new field. An identical replay (same `actionType` and payload under the same key) returns the original cached `ActionResult` with `status: "duplicate"` and does not invoke the provider again - proven by a test asserting the provider's own side-effect callback was invoked exactly once across two identical calls. A request that reuses the same key with a genuinely different payload is never conflated with the cached result; it is evaluated fresh on its own merits (proven by a dedicated test) - silently returning a stale result for a different action would be a correctness bug, not a convenience. Duplicate tracking is in-memory only, scoped to one executor instance's lifetime, and unbounded (disclosed limitation, not a concern for this proof).

**Deterministic ordering.** `executeAll(requests)` is a plain `for` loop awaiting each `execute()` call in turn - proven with a provider whose `execute()` records start/end markers and includes an artificial delay on one request, confirming a slower earlier request always fully completes before a faster later one begins.

**Harmless proof providers.** `overlay.notification` (payload `{message: string}`) and `system.log` (payload `{level?: "info"|"warn"|"error", message: string}`) each deliver to an injectable sink (`context.notify`/`context.log`) that defaults to a `console.log` line - no file, network, or emulator I/O occurs unless a caller explicitly injects a sink that does that (which none of this task's code does).

## Security/Compatibility Considerations

No arbitrary-code-execution path: providers are plain JavaScript objects supplied by the calling code at the source level, not loaded from user input, a manifest, or a rule/action-request payload - there is no new dynamic-evaluation surface. The executor is fail-closed at every stage: an unrecognized action type, an ungranted capability, a failed authorization check, or an invalid payload all refuse execution rather than degrading to a best-effort attempt. The two proof providers perform no real I/O by default (console-line only) and accept no path, network, or emulator-control input of any kind. This is additive-only: no existing schema, evaluator, or event contract changed.
