## Objective

Establish provider-neutral ownership for Pokemon Emerald English retail Rev 0 acquisition and make BizHawk emit that contract through the already proven mapping, Pokemon state/domain, atomic live-state handoff, and overlay.

## Why This Task Exists

`P06-T001` proved BizHawk startup and identity/frame APIs but correctly refused to emit the mGBA-named source contract. Shared Emerald addresses and Gen III decoding were still owned by `adapters/gen3-mgba/`, which would force duplication or false provenance for a second provider. ADR 0020 records the corrected boundary.

## Dependencies

- `P06-T001` completed.
- Existing P05 source validation, safe mapping, Pokemon target validation, atomic `public/live-state.json` handoff, and overlay polling remain unchanged downstream.
- Real-ROM acceptance depends on the operator's legally obtained Emerald Rev 0 image and local BizHawk installation.

## Scope

- Move Emerald identity, addresses, Gen III decoding, contract/schema, fixtures, mapping, and Node orchestration into `adapters/pokemon-emerald-us-rev0/`.
- Add a shared Lua acquisition module loaded by mGBA and BizHawk providers.
- Add provider provenance to the new source contract.
- Adapt BizHawk local configuration and connector to emit the shared source snapshot.
- Verify BizHawk System Bus reads against direct EWRAM/IWRAM offsets before publication.
- Retain mGBA JavaScript compatibility entry points.

## Non-Goals

## Implementation Notes

The chosen contract is `pokemon.emerald.us-rev0.acquisition@1.0.0`. `source` records provider identity, Lua integration, common GBA address-space semantics, primary provider domain/API, and empirically verified direct domains. This is narrow contract-specific provenance, not a universal provenance/confidence model.

BizHawk 2.11.1 upstream source defines `System Bus` (`0x10000000`), `EWRAM` (`0x40000`), and `IWRAM` (`0x8000`). The connector checks those dimensions, then compares each known absolute System Bus read with the translated direct WRAM read of the same width. This runtime check supplies empirical evidence only when the real operator session runs.

## Review Findings

Independent review: **APPROVE**. Verified in a fresh isolated clone, not the implementation clone.

**Provider neutrality (objective 1):** `pokemon.emerald.us-rev0.acquisition@1.0.0`'s schema, fixtures, decoding, and mapping live entirely under `adapters/pokemon-emerald-us-rev0/`, with no emulator name in the contract ID or schema `$id`. `source.provider.id` pattern (`^[a-z0-9]+(?:[.-][a-z0-9]+)*$`) is generic; `memory.addressSpace` is a fixed `const` shared by both providers, while `primaryDomain`/`verifiedDomains` carry real provider-specific diagnostics without becoming downstream dispatch keys. `adapters/gen3-mgba/*.js` are now pure one-line `export *` (or thin single-function) re-exports — confirmed by reading every file. `adapters/bizhawk/proof-connector.lua` and `adapters/gen3-mgba/emerald-acquisition.lua` both `loadfile()` the shared `emerald-acquisition.lua` rather than embedding decode logic; a repo test (`assert.doesNotMatch(...,  /0x020244E9|GROWTH_SUBSTRUCT_INDEX/)`) enforces this for both providers, not just BizHawk.

**Shared Emerald semantics (objective 2) — independently re-derived, not just re-run:** confirmed `adapters/pokemon-emerald-us-rev0/emerald-us-rev0.js` is byte-identical (`diff --strip-trailing-cr`, zero output) to the already-reviewed `adapters/gen3-mgba/emerald-us-rev0.js` from `P05-T004` — this is a pure move, not a rewrite. Hand-traced the Gen III decrypt/permutation algorithm against the checked-in fixture's raw memory values for **both** party slots: party `personality=25` → `growthSubstructIndex=0` → `growthAddress=0x0202450C` → `encryptedGrowthWord=305420131 (0x12345763)` → XOR against `personality` and `otId (0x12345678)` → `speciesId=258`, matching the fixture's `expected.party.first.speciesId`. Repeated for the opponent slot (`personality=6`, `otId=0xAABBCCDD`, `growthSubstructIndex=1`, `growthAddress=0x02024770`) → `speciesId=261`, matching `expected.battle.opponent.speciesId`. Both by-hand results match the fixture exactly, confirming the shared decode logic independent of the test suite.

**BizHawk memory access (objective 3) — verified against real tagged BizHawk 2.11.1 source, not assumed:** `gh api` pulled the actual `MGBAHawk.IMemoryDomains.cs` at tag `2.11.1` — confirms exact domain names/sizes the connector checks: `"IWRAM"` = 32 KiB (`0x8000`), `"EWRAM"` = 256 KiB (`0x40000`), `"System Bus"` = `0x10000000`, all matching the connector's `getmemorydomainsize` assertions exactly. Pulled `MemoryLuaLibrary.cs` and confirmed every Lua API call used (`getmemorydomainlist`, `getmemorydomainsize`, `read_u8`, `read_u16_le`, `read_u32_le`, all `(addr, domain=nil)`) matches a real `[LuaMethod(...)]`-registered signature. The domain-existence check (via `getmemorydomainlist()`) correctly runs *before* any `getmemorydomainsize()` call, which matters because `GetMemoryDomainSize`'s own doc says an unknown domain name silently falls back to the *current* domain's size rather than erroring — the connector isn't fooled by this since it verifies real existence first. `verifiedRead` genuinely compares two independent domain reads of the same underlying memory (System Bus's `BizReadBus` vs. the flat `EWRAM`/`IWRAM` `MemoryDomainIntPtr` buffers, translated via the known `0x02000000`/`0x03000000` GBA hardware bases) and calls `failClosed` on any mismatch, before publication. Identity checks (version/system/ROM hash) run before domain checks, which run before acquisition — correct fail-closed ordering throughout.
- **Non-blocking finding:** the Lua connector's `directDomain(address)` does not account for read width when checking domain boundaries (unlike its JS counterpart `translateGbaSystemBusAddress`, which is explicitly width-aware and tested for boundary-crossing rejection). Not currently exploitable: every fixed address is far from the EWRAM/IWRAM upper boundary, and the only dynamic address (`saveBlock1`) is already bounded with margin by the shared Lua module's own `saveBlock1 + 5 < 0x02040000` check before any read is attempted. Worth tightening for defense-in-depth if new fields are ever added closer to a domain boundary — not required for this task's scope.

**Provenance (objective 4):** confirmed the BizHawk snapshot's `source.provider = {id: "bizhawk", name: "BizHawk", version: ...}` while `game`/`party`/`battle`/`location` fields are byte-for-byte identical in shape to mGBA's. Confirmed the contract ID genuinely changed (`pokemon.emerald.us-rev0.mgba.acquisition` → `pokemon.emerald.us-rev0.acquisition`, both at version `1.0.0`) — a real, distinct string, not the old ID silently reinterpreted under new semantics.

**Downstream reuse (objective 5) — traced and independently re-run, not just read:** wrote and ran a standalone script (not part of the existing test suite) that takes the checked-in fixture, builds a `BIZHAWK_SOURCE`-provenance snapshot, runs it through the *unmodified* `mapEmeraldSourceFile`/existing mapping/`writePokemonLiveState`, and inspects the real written `live-state.json`: `game.adapter: "BizHawk"`, `party[0].speciesId: 258`, `currentHp/maxHp: 31/35`, `battle.opponent.speciesId: 261`, `extensions[...].source.providerId: "bizhawk"` — then repeated with `MGBA_SOURCE` and got `game.adapter: "mGBA"` with identical game-semantic values. `game.adapter` is a single generic `sourcePath: "/source/provider/name"` field mapping — no BizHawk-specific branch anywhere in the mapping, domain, or `src/` (zero-diff confirmed against `src/`). `npm run live:emerald` (`tools/emerald-live-state.mjs`) is reused completely unmodified in logic (one import-path line changed) for both providers.

**mGBA compatibility (objective 6):** `adapters/gen3-mgba/emerald-us-rev0.js` re-exports are confirmed via a repo test (`compatibilityEmerald === canonicalEmerald`, `compatibilityRead === canonicalRead`) to be true object/function-identity re-exports, not copies. Full suite: 142/142 passing, matching the task record's claim exactly.

**Handoff/failure behavior (objective 7):** `writeJsonAtomically` (shared) writes to a temp file, syncs, closes, then renames over the target — the target is never touched if mapping/validation throws first, so invalid source data cannot replace a last-good `live-state.json`. Both Lua connectors' atomic-write helpers follow the same temp-write → flush → close → remove-old → rename pattern already established and accepted for mGBA.

**Validation (objective 8):** fresh clone → `npm ci` (0 vulnerabilities) → `npm test` 142/142 (matches claim) → `node --check` on every changed JS file → JSON validation on every changed adapter JSON file → `git diff --check` clean → repository-wide relative Markdown-link check clean → independently re-ran the fixture→source→mapping→live-state pipeline for both providers (see objective 5) with results matching the task record's claimed smoke (`species 258`, `HP 31/35`) exactly.

**Scope audit (objective 9):** zero-diff confirmed against `src/` (no second domain, no forked mapping/presentation runtime engine). No C# External Tool, no generalized provider framework, no events/actions/rules/multiplayer/cloud changes. Documentation (`implementation-plan.md`, `roadmap.md`, `last-worked-on.md`) consistently states real-ROM BizHawk acceptance and the `P05` gate remain open — no false closure claim anywhere.
