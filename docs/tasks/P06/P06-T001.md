## Objective

Add BizHawk as the second emulator target through a local-only Windows launcher that automatically starts supported Pokemon Emerald and a repository-owned acquisition bootstrap. Prove reliable emulator/system/ROM identity and a changing frame heartbeat without duplicating Pokemon mechanics or changing the mGBA pipeline.

## Why This Task Exists

`P06` must prove a second source can enter the architecture without copying domain behavior into platform/emulator layers. BizHawk has supported command-line Lua loading that can remove Proof 1's manual script-loading step, but that surface and its C# External Tool alternative had not been verified or scaffolded.

## Dependencies

- `P02` is complete and provides the Pokemon domain boundary.
- `P05-T001` through `P05-T006` are complete and provide public source/mapping/domain/overlay contracts, but `P05` remains active pending real mGBA acceptance and richer acquisition.
- Explicit owner direction authorized this independent P06 bootstrap before the full P05 phase gate. This task cannot close P06 or claim source-contract reuse by itself.

## Scope

- Target official Windows x64 BizHawk 2.11.1.
- Add `.env.bizhawk.local` configuration via a committed fake-path example.
- Validate executable, Emerald ROM, optional savestate, connector, and diagnostic paths before launch.
- Auto-launch `EmuHawk.exe` with `--lua`, optional `--load-state`, and the ROM as the final argument.
- Add a generic Lua connector that validates launcher-supplied emulator/system/ROM expectations and writes a changing JSON diagnostic.
- Document the Lua choice, External Tools as a later option, and the source-contract boundary.

## Non-Goals

- No BizHawk acquisition source contract, mapping project, normalized state, or overlay handoff.
- No Pokemon party/battle/move/type/damage/capture logic in the BizHawk connector.
- No changes to the mGBA provider, source contract, mapping, or runtime.
- No C# External Tool implementation or binary.
- No ROMs, BIOS files, saves, savestates, emulator binaries, or machine-specific paths.
- No events, actions, rules, Workbench, multiplayer, sessions, or cloud.

## Acceptance Criteria

- Current official BizHawk Windows release and automation surfaces are verified from upstream primary sources.
- `npm run proof:bizhawk -- --check` fails deterministically on missing required paths and never launches BizHawk.
- Normal launch supplies the connector automatically, keeps the ROM argument last, and conditionally supplies `--load-state`.
- Paths with spaces remain one argument because Node passes an argument array without shell parsing.
- Connector rejects unsupported BizHawk version, system, or ROM hash and writes an `unsupported` diagnostic before stopping.
- Supported execution writes a `connected` diagnostic whose frame value changes while emulation advances.
- Existing mGBA acquisition/mapping/domain behavior remains unchanged.

## Implementation Notes

### Upstream research

- GitHub's official release API reported `2.11.1` (published 2026-05-01), with `BizHawk-2.11.1-win-x64.zip` as the Windows asset.
- BizHawk 2.11.1's README documents Windows `--lua=<path>` followed by a ROM path.
- Its `ArgParser.cs` defines `--lua`, `--load-state`, and `--open-ext-tool-dll`, and explicitly says the ROM should be last.
- `MainForm.cs` loads the command-line ROM, then state, then starts the Lua script from the shown-window callback.
- Official Lua documentation/source confirms `client.getversion`, `emu.getsystemid`, `gameinfo.getromhash`, `emu.framecount`, and `emu.frameadvance`.
- The bundled GBA game database identifies Emerald English retail Rev 0 by SHA-1 `F3AE088181BF583E55DAF962A92BB46F4F1D07B7`.

### Integration choice

Lua is the smallest Proof 2 mechanism because BizHawk auto-loads it directly and it requires no compiled artifact. External Tools are retained as a longer-term option for typed APIs, lifecycle, performance, or native UI, but current tools target .NET Framework 4.8, load from BizHawk's `ExternalTools` directory, reference BizHawk assemblies, and use a trust flow. The 2.11.1 external-tool opening path also runs before command-line ROM loading, complicating ROM-specific applicability.

The connector is intentionally generic: expected version, system, hash, and output path arrive through process environment. It does not call memory APIs. The Emerald-specific launcher owns the supported proof identity.

The existing source ID is `pokemon.emerald.us-rev0.mgba.acquisition@1.0.0`; emitting it from BizHawk would lie about provenance. This task therefore stops at diagnostics. The next slice must deliberately define shared Emerald acquisition ownership and a BizHawk/provider-neutral contract before reusing the existing mapping/domain/overlay pipeline.

## Security/Compatibility Considerations

All machine paths remain in ignored local configuration. The launcher validates every input file before spawning. Node passes arguments directly without a shell. The connector is read-only with respect to emulation, does not use BizHawk memory APIs, and only writes the configured local diagnostic. Unsupported identities fail closed. No source, mapping, schema, normalized-state, mGBA, or cloud behavior changes.

The diagnostic replacement removes the previous diagnostic before renaming the completed temporary file because standard Lua/Windows replacement behavior is limited. This may briefly make the diagnostic absent, which is acceptable for a developer heartbeat; it is not the production source-state handoff contract.

## Review Findings

Independent review: **APPROVE**. Verified in a fresh isolated clone, not the implementation clone:

- **Upstream CLI claims verified against real BizHawk 2.11.1 source**, not taken on trust: `gh api` pulled the actual `2.11.1`-tagged `ArgParser.cs`, `MainForm.cs`, and `Assets/gamedb/gamedb_gba.txt` from `TASEmulators/BizHawk`. Confirmed exactly as documented: `--lua`, `--load-state`, `--open-ext-tool-dll` all exist; the ROM argument's own description says it "can and should be given LAST despite what it says at the top of `--help`"; `MainForm.cs` loads ROM (~L700), then state (~L779), then the Lua script from the `Shown` callback (~L807-817); `--lua` implies `--luaconsole`; the claimed Emerald Rev 0 SHA-1 (`F3AE088181BF583E55DAF962A92BB46F4F1D07B7`) is the exact, only `!`-flagged (good dump) entry in the bundled GBA game database. Every Lua API call in the connector (`client.getversion`, `emu.getsystemid`, `emu.framecount`, `emu.frameadvance`, `gameinfo.getromname`, `gameinfo.getromhash`, `gameinfo.getstatus`) matches an exact `[LuaMethod("...")]`-registered name in the corresponding `CommonLibs` source file. `emu.getsystemid()`'s documented "no ROM loaded returns NULL" independently corroborates the task's own recorded no-ROM smoke output (`system NULL`, `frame 0`).
- **Zero-manual-bootstrap confirmed**: unlike Proof 1 (mGBA has no supported Lua auto-load path, per `mgba-emu/mgba#3289`), BizHawk's `--lua`/`--load-state` genuinely auto-load both the connector and an optional savestate with the process itself auto-launched by the Node launcher. No manual step remains.
- **Fail-closed identity validation confirmed by static trace**: the connector reads `client.getversion()`, `emu.getsystemid()`, `gameinfo.getromhash()` before any heartbeat write, compares against launcher-supplied `BIZHAWK_EXPECTED_*` env vars, writes an `unsupported` diagnostic and calls Lua `error()` to hard-stop on any mismatch, before ever entering the frame-advance loop.
- **Connector genuinely emulator-generic**: no Pokemon/party/species/battle/move/type/damage identifiers and no `memory.*` API calls anywhere in `proof-connector.lua` (confirmed by direct read, and independently enforced by the branch's own regression test). All game-specific expectations arrive via environment variables owned by the launcher, not the connector.
- **No inappropriate reuse of the mGBA source contract**: `adapters/gen3-mgba/` has a zero-line diff against `main`; `src/`, `public/`, and `src/schemas/` are all untouched. The only appearances of `pokemon.emerald.us-rev0.mgba.acquisition@1.0.0` in the new files are explicit "this connector does not emit this" disclaimers.
- **Local config/security verified hands-on**: ran `npm run proof:bizhawk -- --check` for real, first with no `.env.bizhawk.local` present (failed closed, exit 1, no launch attempted) and then with real disposable stand-in files under a path containing spaces (validated correctly, printed the resolved single-argument path, did not launch, matched the unit-tested `createBizHawkLaunch` argument order: `--lua=<connector>`, `--load-state=<savestate>` when configured, ROM last). Confirmed via `git check-ignore` that `.env.bizhawk.local` is caught by the pre-existing `.env.*.local` pattern while `.env.bizhawk.local.example` stays tracked, and that the new `*.SaveRAM`/`*.State`/`*.State[0-9]` patterns (BizHawk's actual save/state extensions, which differ in case from mGBA's) correctly ignore disposable stand-in save/state files created during this review. `selectProofVariables` allowlists exactly the 4 declared `BIZHAWK_PROOF_VARIABLES` keys, confirmed by the branch's own test that an unrelated environment variable never reaches the resolved config.
- **Architectural judgment on the proposed next boundary**: correct. Deferring a BizHawk/provider-neutral Emerald source contract and shared decoding ownership to a dedicated, separately reviewed slice (rather than reusing or duplicating the mGBA-specific contract now) is consistent with the adapter-owned-contract boundary established in `P05-T003`/`P05-T004` and the domain-neutral overlay boundary from `P02-T006`. Gen 3 Pokemon memory layout is not actually mGBA-specific — it is the same game running under any emulator exposing real GBA memory — so a future game-owned (not mGBA-owned, not BizHawk-owned) decoding layer is the architecturally sound direction, not a shortcut.
- **Lua-now/External-Tool-later judgment**: correct and well-supported. The upstream evidence (External Tools require a compiled .NET Framework 4.8 assembly under BizHawk's `ExternalTools` directory, a trust/assembly-coupling flow, and 2.11.1's external-tool-opening path running before command-line ROM loading, which complicates ROM-specific gating) independently matches this session's own prior BizHawk research conclusion ("C# External Tool as production connector" as the long-term target, Lua/CLI as the low-friction bootstrap).
- **Disclosed, non-blocking note**: the connector's diagnostic replacement removes the previous file before renaming the new one into place (a real Lua-on-Windows `os.rename` limitation, not an oversight), creating a brief window where the diagnostic is absent. This is explicitly disclosed in the task record and reasonably scoped as acceptable for a developer heartbeat, not the production source-state handoff contract. No fix required for this task's scope.
- **Real validation run** (fresh clone, not the implementation clone): `npm ci` (5 packages, 0 vulnerabilities), `npm test` (136/136 passing, matching the implementer's reported count), `node --check` on all four new/changed JS files, `git diff --check` clean, zero-diff confirmed on every file/directory the Non-Goals section says must be untouched.
- **Not verified in this review** (same disclosed, non-blocking gap as the implementer's own report): a real supported-ROM heartbeat smoke (`status: connected`, advancing `runtime.frame`) requires a legally obtained Emerald Rev 0 image, which is unavailable in this environment. This matches the established precedent for every prior ROM-dependent task in this project (`P05-T004` through `P05-T007`) and does not block merge of a disclosed, honestly-scoped bootstrap.
