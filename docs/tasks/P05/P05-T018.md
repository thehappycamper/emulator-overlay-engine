## Objective

Preserve browser-local, user-controlled `<details>` disclosure (expand/collapse) state across ordinary live-state re-renders, so an ordinary telemetry update (HP, PP, stat stage, etc.) never silently collapses a panel the user expanded, and never reopens one they collapsed.

## Why This Task Exists

Discovered during real BizHawk acceptance of `P05-T017`'s battle stat-stage work (see `docs/project/last-worked-on.md`'s current session and the addendum on `P05-T017`'s own record): with "Compare Stats" expanded, a live stat change (e.g. Growl) caused the dashboard to re-render and the panel silently collapsed again. This is a separate, general UI-lifecycle defect, not specific to Compare Stats or to stat stages.

## Dependencies

`P05-T017` (the acceptance session that surfaced this), `src/overlay/app.js`/`live-state.js` (the polling/render lifecycle this task modifies), `src/domains/pokemon/presentation.js` (the three existing `<details>` panels this task tags).

## Scope

- New domain-neutral `src/overlay/disclosure-state.js`: `captureDisclosureState`/`restoreDisclosureState`, keyed by a stable `data-disclosure-id` attribute, not DOM position/array index.
- `src/overlay/app.js`: wrap the existing `onRender` `contentEl.innerHTML = ...` replacement with capture-before/restore-after.
- `src/domains/pokemon/presentation.js`: add `data-disclosure-id` to the three existing `<details>` panels (Compare Stats: `battle-stat-compare`; Wild Encounters: `location-encounters`; Poke Balls: `battle-balls`), in both their populated and empty/fallback render branches.
- Tests: fast pure-logic tests of the capture/restore module, three updated literal-markup assertions in the existing presentation suite, and one real, interactive headless-Chrome test proving the full lifecycle.

## Non-Goals

No incremental/virtual DOM rewrite, no persistence beyond the current page load (no `localStorage`/cookies/URL params/server-side state), no dashboard redesign, no Overlay Workshop, no change to Emerald acquisition, stat-stage math, event/rule semantics, or any schema.

## Acceptance Criteria

- Expanding a panel, then an ordinary live-state change (HP/PP/stat-stage/etc.), leaves it expanded.
- Leaving a panel collapsed through the same kind of change leaves it collapsed.
- At least two distinct panel kinds are proven, not just Compare Stats.
- Multiple panels with different states preserve independently in the same re-render.
- A panel that disappears (its condition becomes false) does not leak its prior state onto an unrelated panel, and if it later reappears it gets its own real default, not the stale prior state.
- Initial page load still shows every panel at its real default (collapsed).
- No new persistent/cross-session storage mechanism introduced.

## Implementation Notes

**Root cause.** `src/overlay/live-state.js`'s polling controller already only calls `onRender` when the fetched state actually changed (`app.js`'s docstring already described this as "change-only rendering"). The defect was entirely inside `onRender` itself (`src/overlay/app.js`): `contentEl.innerHTML = renderDomainOverlay(domain, state)` fully replaces the dashboard's DOM subtree on every such change. A native `<details open>` state is live DOM state that exists only in the browser, never round-tripped through the rendered `state` object at all - `renderStatComparison`/`renderEncounters`/`renderBallsPanel` always emit `<details>` with no `open` attribute, by design (collapsed by default). A full innerHTML replacement therefore discards that DOM-local state unconditionally, on every single poll that detects any change anywhere in the state - not just changes to the panel's own content.

**Design.** `data-disclosure-id` is an explicit, author-chosen semantic identity per panel, independent of DOM position, array index, or even the CSS class already on the same element. `captureDisclosureState(container)` walks `container.querySelectorAll('details[data-disclosure-id]')` before the swap and returns a `Map<id, open>`; `restoreDisclosureState(container, state)` walks the same selector after the swap and applies `state.get(id)` onto any element whose id is present in the map. An id with no matching element after the swap (the panel disappeared) is simply unused - never applied elsewhere. An element present now whose id was never captured (first render, or a genuinely new panel) is left at whatever the fresh markup's own default is. Because matching is always by explicit id, one panel's state can never leak onto a different, unrelated panel that happens to occupy the same DOM position - this is a structural property of the design, not something enforced by extra logic.

`disclosure-state.js` lives in `src/overlay/` (the existing domain-neutral browser-bootstrap/platform layer - see `docs/maps/code-map.md`), not inside the Pokemon domain package: preserving ephemeral browser UI state across a re-render is a generic platform concern with no Pokemon semantics in it. `presentation.js` only needed to add one attribute per existing `<details>` tag - the *convention* (an opt-in `data-disclosure-id` attribute), not the mechanism, is what a future domain's markup would need to participate.

This is deliberately the "capture and restore around an existing full-replacement rerender" approach, not a move toward incremental/virtual DOM - explicitly the smaller, architecture-consistent option per the task brief. It does not make a future move to stable-component rendering harder: the `data-disclosure-id` convention (a stable per-panel identity) is exactly the kind of thing an incremental renderer would also need.
