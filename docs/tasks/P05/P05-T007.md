## Objective

Determine empirically whether EOE can directly host the mGBA libretro core and acquire Pokemon Emerald memory through the official libretro API — no RetroArch, no Lua, no emulator GUI automation, no process-memory hooking. **This is a feasibility spike, not the start of a production emulator frontend**, and this task does not claim production readiness regardless of outcome.

## Why This Task Exists

Follow-up to the prior Libretro/RetroArch research turn's recommendation ("a small [experiment] yes — a full prototype... no") and its named smallest-experiment proposal. That research established the mGBA libretro core registers EWRAM/IWRAM at real hardware addresses via `RETRO_ENVIRONMENT_SET_MEMORY_MAPS` (confirmed from mGBA's own `libretro.c` source), but that was a documentation-only finding — this task tests it against a running core.

## Dependencies

- `adapters/gen3-mgba/emerald-us-rev0.js` (existing, reviewed Gen III address constants — reused, not duplicated).
- Started from approved `origin/main` after checking existing task records and active remote task branches; no `P05-T007` or later collision found.

## Scope

- `experiments/libretro-direct-host/` — an isolated Node.js host implementing only the libretro ABI plumbing needed to load a core, run frames, and read one known address.

- Local, gitignored configuration for the core path and ROM path (operator-supplied, nothing committed).

- No BizHawk-related changes — this branch is independent of and does not touch anything in Codex's concurrent work.

## Acceptance Criteria

- A real, official, redistributable mGBA libretro core can be dynamically loaded and its `retro_get_system_info()` output captured.
- The full required callback surface (environment, video, audio ×2, input ×2) can be registered and `retro_init()` completed without the core failing or hanging.
- `retro_load_game()` is attempted and its result (success or failure) is captured and handled without crashing, whichever occurs.
- If a game loads successfully: memory descriptors are captured via the environment callback, EWRAM is located, and at least one known Emerald address is read and reported.
- If a game does not load successfully in this environment (expected, given no legally obtainable ROM is available to this agent — see Result): the exact point and reason execution stopped is documented precisely, not glossed over.
- Address-translation logic is unit tested independent of any live core/ROM, against the real mGBA descriptor shape and including nontrivial `select`/`disconnect`/`offset`/bit-collapsing cases, matching RetroArch's own canonical reference algorithm.
- `retro_api_version()` is explicitly called and its result validated against `RETRO_API_VERSION`, not merely available, and a mismatch fails closed immediately before any further ABI call or callback registration.
- Callback registration and every `retro_set_*` call live inside the same guarded lifecycle as `retro_init`/`retro_load_game`/`retro_run`, so a failure at any point - including partway through registration - unregisters exactly the callbacks that were actually registered so far.
- Address-descriptor lookup honors Libretro's documented first-descriptor-claims precedence exactly, including when the first matching descriptor has no backing pointer, and this is proven with a regression test using overlapping descriptors, not just asserted.
- `retro_deinit()` and callback cleanup are attempted deterministically via `try`/`finally` regardless of which path execution took, with each outcome recorded rather than assumed.
- A clear, evidence-based recommendation is produced from one of the four specified options.

## Implementation Notes

**Toolchain constraint:** no C/C++ compiler is available in this environment (confirmed: `gcc`/`g++`/`cl`/`clang`/`cc` all absent). A from-scratch native frontend (`nanoarch`-style) was not possible here. Used Node.js + [`koffi`](https://koffi.dev/) instead — an FFI library shipping prebuilt native bindings, requiring no compiler. This is a deliberate, disclosed dependency scoped **only** to this isolated experiment directory (its own `package.json`, not referenced by the root `package.json`); it adds nothing to the production dependency tree. `koffi`'s exact API (`koffi.proto`/`koffi.register`/`koffi.struct`/`koffi.decode`/`koffi.view`) was verified against its live documentation and its actual installed behavior, not assumed — an initial attempt using a different (and, it turned out, non-current) API shape (`koffi.callback`) failed immediately and was corrected before proceeding.

**Core source:** the official mGBA libretro core nightly build was downloaded directly from `buildbot.libretro.com` for local testing (not committed to the repository) — this is the libretro project's own official, MPL-2.0-licensed, redistributable emulator core binary, the same category of artifact as installing mGBA or BizHawk itself, containing no game content.

**ABI details** (field layouts, environment command numbers, calling convention) were transcribed from the authoritative `libretro.h` header (RetroArch master branch), not inferred, with each struct/constant in `libretro-abi.mjs` citing what it was checked against.

**Address translation semantics (corrected after independent review):** the original implementation's `select`/`disconnect` handling was self-derived from a plain reading of `libretro.h`'s doc comment, not from a canonical reference implementation, and independent review correctly flagged it as not matching real RetroArch frontend behavior. It has been replaced with a direct transcription of RetroArch's own reference algorithm, `rc_libretro_memory_get_descriptor()` in `deps/rcheevos/src/rc_libretro.c` (RetroArch master branch) — the actual production code the RetroArch frontend uses to translate `retro_memory_descriptor` arrays into readable addresses for its achievements/cheats subsystem, and the most concrete available definition of "RetroArch frontend behavior" for this exact problem. Two corrections resulted:

1. **`select === 0` must not consult `disconnect` at all.** `libretro.h` documents a zero `select` as meaning `start`/`len` are "the complete mapping for this region of memory (i.e. each byte is mapped exactly once)" — no mirroring is possible in that case, so `disconnect` is irrelevant. The reference implementation's `select === 0` branch is a plain range check with no `disconnect` handling whatsoever; the module now matches this exactly, and a test (`zero-select descriptors ignore disconnect entirely...`) pins this behavior down explicitly, including for the atypical (non-real-world, but worth pinning) combination of `select: 0` with a non-zero `disconnect`.
2. **`disconnect` bits must be *collapsed*, not merely zeroed.** The previous `relative & ~descriptor.disconnect` left gaps in the numeric value instead of closing them — correct only by coincidence for a single isolated disconnect bit, and wrong for any real multi-bit bank-mirroring descriptor (it would produce a sparse, usually out-of-bounds offset instead of a compact one). The reference implementation instead repeatedly peels off the lowest set bit of the disconnect mask and shifts the remaining higher bits down to close the gap (RetroArch's own comment credits this to its `mmap_reduce` function). `collapseDisconnectBits()` is a direct transcription of that loop. Additionally, the reference implementation treats "select matches, but the collapsed offset still exceeds `len`" as **no match** (falls through to the next descriptor), which is a real, load-bearing part of correctness that cannot be expressed if matching and offset computation are separate steps — the module now resolves both together internally (`resolveOffsetWithinDescriptor`) for exactly this reason.

Both corrections are backed by hand-derived, independently bit-verified test cases (not just re-running the implementation against itself) in `test/address-translate.test.js`, including a non-adjacent multi-bit disconnect mask (bits 1 and 5) to exercise the collapse loop beyond the trivial single-bit or adjacent-bits case.

**Real mGBA descriptor shape correction:** the prior test suite's EWRAM/IWRAM stand-in descriptors used `select: 0`, which is **not** what the real core registers. Confirmed against mGBA's actual `src/platform/libretro/libretro.c` (`_setupMaps()`, GBA branch): both EWRAM and IWRAM are registered with `select: 0xFF000000` (only the top address byte selects the region — the low 24 bits index directly into the buffer, bounded by `len`) and `disconnect: 0`. The old `select: 0` tests were therefore exercising a materially different code path (the zero-select branch) than what actually runs against the real core (the non-zero-select branch). All descriptor-shaped tests now use the real `select: 0xFF000000` values, and a dedicated test confirms an address with the right top byte but an out-of-range low-24-bit offset (e.g. `0x02040000`, beyond EWRAM's real 256 KiB) is correctly rejected rather than falsely matched.

**`decodeMemoryMap()` dropped `descriptor.offset`:** a second real bug found during the fix pass — the FFI decode step in `libretro-abi.mjs` copied every `retro_memory_descriptor` field into its plain-JS-object return value except `offset`, silently discarding it. `libretro.h` documents `offset` as the field address calculations should use in preference to pointer arithmetic; a dropped `offset` would have produced silently wrong buffer reads for any descriptor with a non-zero offset (real cores use this for regions sharing a backing pointer, e.g. mirrored ROM banks), while looking correct for the zero-offset case this spike's original ad hoc smoke test happened to exercise. Fixed, and regression-tested with a real `koffi` struct encode/decode round-trip (`test/libretro-abi.test.js`), not just a code read — including a case asserting a *zero* offset survives as `0`, not as `undefined`.

**`retro_api_version()` now explicitly called and validated.** `host.mjs` calls it immediately after loading the core, before any other ABI call, compares it against `RETRO_API_VERSION` (`1`, newly exported from `libretro-abi.mjs`), and records both the actual value and the match result in the printed report. Re-run against the real core: `1 === 1`, matches.

**Deterministic cleanup added via `try`/`finally`.** `host.mjs`'s `retro_init`/`retro_load_game`/`retro_run` sequence is now wrapped in a single `try`/`finally` that always attempts `retro_unload_game()` (if a game loaded), `retro_deinit()` (if `retro_init()` was reached), and `koffi.unregister()` for every registered callback — regardless of which path the `try` block took (early return on ROM rejection, full success, or a thrown error) — with every step's outcome recorded in the report rather than assumed. See `README.md`'s "Process exit and koffi callback cleanup" section for a real, disclosed, environment-specific finding surfaced while implementing this: an isolated minimal repro (register a callback that is never invoked by native code, then exit) segfaulted 100% reproducibly (5/5 runs, both Node v20.20.2 and v24.15.0) in this environment, but this spike's actual usage — every callback genuinely invoked by native code before teardown — does not exhibit this; five consecutive full re-runs against the real core all exited `0` with `6/6` callbacks cleanly unregistered.

**Root `npm test` dependency safety.** The new `test/libretro-abi.test.js` imports `koffi`, unlike the pre-existing `test/address-translate.test.js`. Because Node's default recursive test discovery picks up every `*.test.js` file from the repository root regardless of which `package.json` "owns" it, this file guards its own `koffi` import and degrades to a single, clearly-labeled skipped test (rather than throwing and failing the entire root suite) when `koffi` is not resolvable — verified both ways: present (3 real assertions run) and absent via a simulated fresh clone (root `npm test` still exits `0`, with exactly one skipped test named to explain why).

**First-descriptor-claims precedence (second review round).** Independent review correctly found that `findDescriptorForAddress`/`readAddress` were skipping any descriptor with `ptr: null` and continuing to the next one in the array. This does not match libretro.h's documented precedence rule: "If multiple memory descriptors can claim a particular byte, the first one defined in the retro_memory_descriptor array applies" — this applies regardless of whether that first-claiming descriptor has a backing pointer; a `NULL` `ptr` is libretro.h's documented way to say "no accessible memory here," not "skip to the next descriptor." RetroArch's own reference implementation (`rc_libretro_memory_get_descriptor`) matches this: it returns whichever descriptor matches first, `ptr` or no `ptr`, and leaves ptr-nullness handling to the caller. Fixed by introducing `matchDescriptorForAddress()` as the single precedence-respecting lookup both `findDescriptorForAddress` and `readAddress` now delegate to: it finds the first descriptor whose start/select/disconnect/len criteria match (ignoring `ptr` entirely for matching purposes), and only then do the two public functions decide what to do with a `ptr`-less match — which is to throw, explicitly refusing to fall through to a later, possibly-accessible, overlapping descriptor. Two new regression tests use genuinely overlapping descriptors (not just descriptors that happen not to overlap) to prove both directions: an inaccessible first match blocks an accessible second one (the bug this fixes), and an accessible first match wins over a second, distinguishable-by-offset, also-matching descriptor (proving the second is never consulted even when the first succeeds).

**`retro_api_version()` fail-closed ordering (second review round).** The first fix pass called and validated `retro_api_version()` but only logged a warning on mismatch and proceeded anyway. Independent review correctly identified this as not actually failing closed. `host.mjs` now throws immediately on a mismatch, as the very first statement inside the lifecycle's `try` block, before `retro_get_system_info()`, before any `koffi.register()` call, and before any `retro_set_*` call — a core reporting an unexpected API version is not one this spike can safely assume ABI compatibility with for any of those later calls.

**Guarded lifecycle cleanup for partial callback registration (second review round).** The first fix pass's `try`/`finally` only wrapped `retro_init`/`retro_load_game`/`retro_run`; callback registration (`koffi.register()` ×6) and the corresponding `retro_set_*` calls ran before the `try` block started, so a failure during registration itself (e.g. the 4th of 6 registrations throwing) would have left the first 3 callbacks permanently registered with no cleanup path. Fixed by moving registration and `retro_set_*` setup inside the same `try` block, with `registeredCallbacks` (tracked outside the `try` so the `finally` can always see it) appended to immediately as each registration succeeds — so the `finally` block now unregisters exactly what was actually registered, whether that is zero (an `retro_api_version()` mismatch threw first), a partial set (a later registration failed), or all six (normal operation).

**Self-proving evidence for what a rejected run does and does not reach (second review round).** Independent review correctly asked for the README/task record to explicitly state that a rejected non-ROM run never reaches `retro_run()`, `SET_MEMORY_MAPS`, or a memory read, and that only the environment callback is actually invoked. Rather than only asserting this in prose, `host.mjs` now increments a real per-callback counter (`callbackInvocationCounts`) from inside every registered callback's body and includes it in the printed report, alongside an explicit `retroRunInvoked` boolean. Re-run against the real core: `callbackInvocationCounts` shows `environment: 9`, `videoRefresh`/`audioSample`/`audioSampleBatch`/`inputPoll`/`inputState` all `0`, `retroRunInvoked: false`, `memoryMap: null` — the report is now the evidence, not a claim about it.

**`len: 0` (borderless descriptor) limitation documented as out of scope (second review round).** libretro.h documents a zero `len` as meaning a descriptor is "bounded only by select/disconnect" rather than a fixed size. This module's `select !== 0` branch checks `reduced < len`, which (correctly, matching RetroArch's own reference behavior for the same input) can never be true when `len` is `0` — such a descriptor can never match, for any address. This was previously true but unstated; it is now documented explicitly as a disclosed, out-of-scope limitation in both `address-translate.mjs`'s module comment and `README.md`, with a dedicated test (`out-of-scope: a len:0 (borderless) descriptor never matches...`) pinning the behavior. Real GBA descriptors (mGBA's own registration, confirmed against its source) always specify a concrete `len`, so this spike does not need, and does not implement, meaningful support for the borderless case.

**Save-state consideration:** as anticipated by the task, directly loading the project's existing mGBA `.ss0` savestate into the libretro core was considered and explicitly **not attempted**. libretro's `retro_serialize`/`retro_unserialize` is a core-private opaque blob with no documented guarantee of byte-compatibility with standalone mGBA's own savestate file format, even though both wrap libmgba — forcing compatibility would be exactly the kind of hack this task was told to avoid. This remains an open question requiring either the libretro core producing its own savestate after manual play, or a scoped, separately-approved investigation. Not a blocker for this spike, which read memory after a fixed frame count from power-on instead.

## Result — what was and was not empirically verified

This task record was corrected after two independent-review rounds found real
defects in the implementation. The first round: dropped `descriptor.offset`,
an incorrect `select`/`disconnect` algorithm not matching RetroArch's own
reference behavior, tests built on an inaccurate EWRAM/IWRAM descriptor
shape, no `retro_api_version()` validation, no deterministic cleanup. The
second round: `findDescriptorForAddress`/`readAddress` incorrectly fell
through a first-matching-but-`ptr`-less descriptor to a later, overlapping
one instead of honoring Libretro's documented first-descriptor-claims
precedence; `retro_api_version()` was validated but did not actually fail
closed on mismatch; callback registration itself sat outside the guarded
cleanup lifecycle, so a partial-registration failure would have leaked
callback slots; the evidence did not explicitly prove (only asserted) that a
rejected run never reaches `retro_run()`/`SET_MEMORY_MAPS`/a memory read; the
`len: 0` descriptor limitation was true but undocumented; and stale commit
references from the first fix pass were never filled in. All of the below
reflects the **corrected** code, re-verified against a freshly re-downloaded
copy of the real official mGBA libretro core, not either prior (partially
incorrect) run.

**Verified, against the real official mGBA libretro core, via the actual committed code (not just exploratory scratch scripts), across multiple consecutive fresh runs each fix pass:**

- `retro_api_version()` → `1`, explicitly compared against `RETRO_API_VERSION` (`1`), recorded as a match, and now gates all further ABI calls/setup on that match (fails closed immediately on any mismatch, before `retro_get_system_info()` or any callback registration) — not merely called, validated, and logged.
- `retro_get_system_info()` → `{ library_name: "mGBA", library_version: "0.11-219-e31759b", valid_extensions: "gba|gb|gbc|sgb", need_fullpath: false, block_extract: false }` — a real, live-decoded struct via an out-parameter, not a guess; identical across every re-run to date (same nightly build).
- Full callback registration (environment, video, audio, audio-batch, input-poll, input-state) succeeded, now from inside the same guarded lifecycle as `retro_init`/`retro_load_game`/`retro_run`; `retro_init()` completed cleanly.
- The environment callback correctly intercepted **9 real commands** the core issued during init, decoded against `libretro.h`'s exact numeric values: `GET_VFS_INTERFACE` (×2), `GET_CORE_OPTIONS_VERSION`, `SET_VARIABLES`, `SET_PIXEL_FORMAT`, `SET_INPUT_DESCRIPTORS`, `GET_INPUT_BITMASKS`, `GET_VARIABLE`, `GET_LOG_INTERFACE`. All were declined (`false`) with no crash, hang, or misbehavior — confirming the core tolerates a minimal/stub environment implementation for reaching this point.
- `retro_load_game()`, attempted with a 310,356-byte non-ROM file (a freshly re-downloaded copy of the public `libretro.h` header, used only as a "clearly not a valid GBA ROM" negative-test input — never anything resembling real game content), correctly and safely returned `false`. No crash, no hang.
- **What a rejected run does and does not reach, proven by real counters, not just asserted:** the printed report's `callbackInvocationCounts` shows `environment: 9` and `videoRefresh`/`audioSample`/`audioSampleBatch`/`inputPoll`/`inputState` all `0`, with `retroRunInvoked: false` and `memoryMap: null` — direct evidence that a rejected non-ROM run never reaches `retro_run()`, never receives `SET_MEMORY_MAPS`, never attempts a memory read, and never invokes any callback besides the environment callback. Reproduced across 4 consecutive fresh runs in this fix pass alone.
- **Deterministic cleanup**, exercised on every run regardless of the ROM-rejection early exit, now covering the entire lifecycle including callback registration: `retro_deinit()` reported `"ok"` and `koffi.unregister()` reported `6/6` callbacks released with zero errors, on every run across both fix passes. Process exit code was `0` every time. (`retro_unload_game()` was correctly *not* attempted, since no game ever loaded to unload — recorded as `"not attempted"`, not silently skipped.)
- Pure address-translation logic: 16/16 tests passing against the real mGBA EWRAM/IWRAM descriptor shape (`select: 0xFF000000`, not the previous, inaccurate `select: 0` stand-in), including hand-derived-and-independently-bit-verified nontrivial multi-bit disconnect-collapse cases, first-descriptor-claims precedence with genuinely overlapping descriptors (both the inaccessible-first-blocks-accessible-second and accessible-first-wins-over-second cases), and the `len: 0` out-of-scope case.
- `decodeMemoryMap()`'s FFI decode path: 3/3 tests passing via real `koffi` struct encode/decode round-trips, confirming `offset` now survives decode (including the zero-offset case, which must decode to `0`, not `undefined`).

**Not verified — blocked on one specific, well-understood cause, unchanged by this fix pass:** no legally obtainable Pokemon Emerald ROM is available to this agent in this environment. `SET_MEMORY_MAPS` is (correctly, per libretro convention) only published by the core after a *successful* game load, which never occurred here or in the original run. Consequently, **still not observed live**: real memory descriptors, EWRAM's actual published start/length, an actual byte value read from a known address, stability of that value across repeated `retro_run()` calls, or CPU/performance characteristics under real execution. The claim that our existing address constants resolve correctly against mGBA's real EWRAM descriptor now rests on: (a) structural confirmation from mGBA's own `libretro.c` source (both the descriptor registration and, newly, the exact `select`/`disconnect` values it uses), and (b) this task's corrected, canonically-algorithm-matching, hand-verified translation logic — still not a live read. This mirrors, in every material respect, the "manual mGBA GUI smoke test remains pending" pattern already established and accepted across every prior `P05` task in this phase, and this fix pass does not claim otherwise: it makes the branch correct and ready for that real-ROM test, not a substitute for it.

## Decision

**LIBRETRO DIRECT HOST IS PROMISING — continue prototype**, with the explicit caveat that the one remaining unproven claim (a real value read from real emulated memory) requires an operator-supplied, legally obtained ROM to close — the same category of gap every other `P05` acquisition task in this phase has carried at this stage, not a new or worse one.

Every failure mode this spike could plausibly have hit up to the point it actually reached did not occur: the core did not require a compiler to interoperate with (a real concern going in, given this environment has none), did not crash or hang on a rejected load, and the environment-callback mechanism — the trickiest plumbing, since it requires the core to call back into JS during otherwise-synchronous native calls — worked correctly on the first corrected attempt. The host does not require real video/audio/input handling by design; those callbacks currently use minimal/no-op implementations. This has not yet been validated through `retro_run()`, because no valid ROM was loaded during the recorded spike runs — `retro_run()` was never invoked, so whether a core tolerates no-op video/audio/input across the full frame-execution path (not just up through `retro_init()`) remains an open question for the real-ROM acceptance session, not a settled one. The total implementation is small: three files, roughly 250 lines combined, using one well-established, prebuilt-binary FFI dependency, isolated from the rest of the repository.

### Comparison against the other acquisition paths

| | mGBA Lua (proven, `P05-T001`–`T006`) | BizHawk External Tool (Codex, in progress) | Stock RetroArch/NCI (researched, not built) | Libretro direct host (this spike) |
|---|---|---|---|---|
| Manual step remaining | Load script each session (confirmed unavoidable, upstream "not planned") | None (`--open-ext-tool-dll`) | None (config-file plumbing, no CLI flag) | None once a ROM is loaded — **but ROM loading itself would need to be driven by our own code, not a GUI** |
| Requires a GUI emulator at all | Yes | Yes | Yes | **No** — this is the only path with no GUI application in the loop |
| Toolchain needed | None beyond mGBA itself | .NET/C# build | None | Node + prebuilt FFI binary (no compiler); a native build would need a C toolchain this environment lacks |
| Evidence quality this session | Extensive, live, real ROM (fixture-derived) | Pending Proof 2 | Documented, not run | Extensive up to the ROM-load boundary; blocked past it by ROM availability, not by the architecture |
| Multi-system reach | GBA-only | Wide (core-agnostic API) | Widest (200+ cores) | Wide (core-agnostic API), same ceiling as BizHawk |

The direct-host path is the only one of the four that removes the GUI emulator from the runtime picture entirely — a meaningfully different, and for a future headless/telemetry-focused architecture, more attractive shape than any of the other three. It is not, on this evidence, a replacement for the near-term BizHawk/mGBA work; it is a second, independently-promising direction worth a continued, still-small next increment once a real ROM can close the remaining gap.

## Review Findings

Independent review is required per `AGENTS.md` because this introduces a new dependency (scoped) and executes third-party native code (a dynamically loaded core) — genuinely new risk surface for this repository.

**First independent review round** found blocking correctness defects (see Implementation Notes for the fixes): `descriptor.offset` silently dropped during FFI decode; `select`/`disconnect` address-translation logic not matching canonical Libretro/RetroArch behavior; regression tests built on an EWRAM/IWRAM descriptor shape (`select: 0`) that does not match what the real mGBA core registers (`select: 0xFF000000`); no nontrivial disconnect/select/offset/bit-collapsing test coverage; `retro_api_version()` never called; no deterministic `retro_deinit()`/koffi callback cleanup; evidence/documentation not clearly distinguishing executed from untested claims. Addressed in the first fix pass (`c8c504c`).

**Second independent review round** found further blocking issues in that fix: `findDescriptorForAddress`/`readAddress` did not honor Libretro's documented first-descriptor-claims precedence when the first matching descriptor had no backing pointer, incorrectly falling through to a later, overlapping descriptor instead of rejecting; `retro_api_version()` was validated but did not actually fail closed on mismatch before further ABI calls/setup; callback registration/`retro_set_*` setup sat outside the guarded cleanup lifecycle, so a partial-registration failure would have leaked callback slots; the README/task record asserted (rather than proved) that a rejected run never reaches `retro_run()`/`SET_MEMORY_MAPS`/a memory read; the `len: 0` descriptor limitation was real but undocumented; and the first fix pass's own "Fix commit(s)" reference was left as an unfilled placeholder rather than the real commit hash. All addressed in this second fix pass (`4fdcf46`, plus `394baed` for an unrelated leftover merge-conflict-marker cleanup caught while rebasing) — see Implementation Notes and the corrected Result section above.

**Third independent review round** found one blocking documentation-accuracy defect, no runtime/implementation defects: the Decision section's summary sentence ("did not require real video/audio/input to reach `retro_run`") and two equivalent passages in `experiments/libretro-direct-host/README.md` (the "this spike found no such requirement for reaching `retro_run()`" sentence, and the save-state section's "this spike instead reads memory immediately after a fixed number of `retro_run()` calls" sentence) stated or implied that the spike had empirically exercised `retro_run()` with no-op video/audio/input and found it sufficient. This is inaccurate: no valid ROM was available in this environment in any recorded run, `retro_load_game()` never succeeded, and `retro_run()` was consequently never invoked at all - a fact this same task record's own Result section already stated correctly and explicitly elsewhere ("still not observed live"). The three passages conflated "the host is designed not to need real video/audio/input" (true, and unaffected by ROM availability) with "this was validated through actual frame execution" (false). All three corrected to explicitly separate the by-design claim from the not-yet-empirically-validated one; no runtime/implementation code was changed, since the underlying behavior was never mischaracterized in the code or its self-proving evidence (`retroRunInvoked: false` was already correctly reported) - only the prose summarizing it overstated what had been exercised. Independent re-review is required before merge; this task does not self-approve.
