## Objective

Determine empirically whether EOE can directly host the mGBA libretro core and acquire Pokemon Emerald memory through the official libretro API — no RetroArch, no Lua, no emulator GUI automation, no process-memory hooking. **This is a feasibility spike, not the start of a production emulator frontend**, and this task does not claim production readiness regardless of outcome.

## Why This Task Exists

Follow-up to the prior Libretro/RetroArch research turn's recommendation ("a small [experiment] yes — a full prototype... no") and its named smallest-experiment proposal. That research established the mGBA libretro core registers EWRAM/IWRAM at real hardware addresses via `RETRO_ENVIRONMENT_SET_MEMORY_MAPS` (confirmed from mGBA's own `libretro.c` source), but that was a documentation-only finding — this task tests it against a running core.

- `adapters/gen3-mgba/emerald-us-rev0.js` (existing, reviewed Gen III address constants — reused, not duplicated).
- Started from approved `origin/main` after checking existing task records and active remote task branches; no `P05-T007` or later collision found.

## Acceptance Criteria

- A real, official, redistributable mGBA libretro core can be dynamically loaded and its `retro_get_system_info()` output captured.
- The full required callback surface (environment, video, audio ×2, input ×2) can be registered and `retro_init()` completed without the core failing or hanging.
- `retro_load_game()` is attempted and its result (success or failure) is captured and handled without crashing, whichever occurs.
- If a game loads successfully: memory descriptors are captured via the environment callback, EWRAM is located, and at least one known Emerald address is read and reported.
- If a game does not load successfully in this environment (expected, given no legally obtainable ROM is available to this agent — see Result): the exact point and reason execution stopped is documented precisely, not glossed over.
- Address-translation logic is unit tested independent of any live core/ROM.
- A clear, evidence-based recommendation is produced from one of the four specified options.

## Implementation Notes

**Toolchain constraint:** no C/C++ compiler is available in this environment (confirmed: `gcc`/`g++`/`cl`/`clang`/`cc` all absent). A from-scratch native frontend (`nanoarch`-style) was not possible here. Used Node.js + [`koffi`](https://koffi.dev/) instead — an FFI library shipping prebuilt native bindings, requiring no compiler. This is a deliberate, disclosed dependency scoped **only** to this isolated experiment directory (its own `package.json`, not referenced by the root `package.json`); it adds nothing to the production dependency tree. `koffi`'s exact API (`koffi.proto`/`koffi.register`/`koffi.struct`/`koffi.decode`/`koffi.view`) was verified against its live documentation and its actual installed behavior, not assumed — an initial attempt using a different (and, it turned out, non-current) API shape (`koffi.callback`) failed immediately and was corrected before proceeding.

**Core source:** the official mGBA libretro core nightly build was downloaded directly from `buildbot.libretro.com` for local testing (not committed to the repository) — this is the libretro project's own official, MPL-2.0-licensed, redistributable emulator core binary, the same category of artifact as installing mGBA or BizHawk itself, containing no game content.

**ABI details** (field layouts, environment command numbers, calling convention) were transcribed from the authoritative `libretro.h` header (RetroArch master branch), not inferred, with each struct/constant in `libretro-abi.mjs` citing what it was checked against.

**Address translation semantics:** implementing `descriptorMatches`'s `disconnect`-bit handling surfaced a real bug during development — the initial version only masked `disconnect` bits when computing the final buffer *offset*, not when checking whether an address *matched* a descriptor at all, so a deliberately-constructed mirrored-region test case failed. Fixed by masking `disconnect` bits before either the `select`-mask or plain-range comparison. Caught by the task's own test suite before this was ever run against a live core — see `test/address-translate.test.js`.

**Save-state consideration:** as anticipated by the task, directly loading the project's existing mGBA `.ss0` savestate into the libretro core was considered and explicitly **not attempted**. libretro's `retro_serialize`/`retro_unserialize` is a core-private opaque blob with no documented guarantee of byte-compatibility with standalone mGBA's own savestate file format, even though both wrap libmgba — forcing compatibility would be exactly the kind of hack this task was told to avoid. This remains an open question requiring either the libretro core producing its own savestate after manual play, or a scoped, separately-approved investigation. Not a blocker for this spike, which read memory after a fixed frame count from power-on instead.

## Result — what was and was not empirically verified

**Verified, against the real official mGBA libretro core, via the actual committed code (not just exploratory scratch scripts):**

- `retro_api_version()` → `1` (matches `RETRO_API_VERSION` in `libretro.h`).
- `retro_get_system_info()` → `{ library_name: "mGBA", library_version: "0.11-219-e31759b", valid_extensions: "gba|gb|gbc|sgb", need_fullpath: false, block_extract: false }` — a real, live-decoded struct via an out-parameter, not a guess.
- Full callback registration (environment, video, audio, audio-batch, input-poll, input-state) succeeded; `retro_init()` completed cleanly.
- The environment callback correctly intercepted **9 real commands** the core issued during init, decoded against `libretro.h`'s exact numeric values: `GET_VFS_INTERFACE` (×2), `GET_CORE_OPTIONS_VERSION`, `SET_VARIABLES`, `SET_PIXEL_FORMAT`, `SET_INPUT_DESCRIPTORS`, `GET_INPUT_BITMASKS`, `GET_VARIABLE`, `GET_LOG_INTERFACE`. All were declined (`false`) with no crash, hang, or misbehavior — confirming the core tolerates a minimal/stub environment implementation for reaching this point.
- `retro_load_game()`, attempted with a 310,356-byte non-ROM file (this repository's own `libretro.h` scratch copy, used only as a "clearly not a valid GBA ROM" negative-test input — never anything resembling real game content), correctly and safely returned `false`. No crash, no hang.
- Pure address-translation logic: 8/8 tests passing, including the disconnect-bit bug found and fixed during this task (see Implementation Notes).

**Not verified — blocked on one specific, well-understood cause:** no legally obtainable Pokemon Emerald ROM is available to this agent in this environment. `SET_MEMORY_MAPS` is (correctly, per libretro convention) only published by the core after a *successful* game load, which never occurred here. Consequently, **not observed live**: real memory descriptors, EWRAM's actual published start/length, an actual byte value read from a known address, stability across repeated `retro_run()` calls, or CPU/performance characteristics under real execution. The claim that our existing address constants require only a subtraction (no bit-masking) against mGBA's real EWRAM descriptor rests on: (a) structural confirmation from mGBA's own `libretro.c` source (prior research), and (b) this task's own correctly-implemented and tested translation logic — not on a live read. This mirrors, in every material respect, the "manual mGBA GUI smoke test remains pending" pattern already established and accepted across every prior `P05` task in this phase.

## Decision

**LIBRETRO DIRECT HOST IS PROMISING — continue prototype**, with the explicit caveat that the one remaining unproven claim (a real value read from real emulated memory) requires an operator-supplied, legally obtained ROM to close — the same category of gap every other `P05` acquisition task in this phase has carried at this stage, not a new or worse one.

Every failure mode this spike could plausibly have hit did not occur: the core did not require a compiler to interoperate with (a real concern going in, given this environment has none), did not require real video/audio/input to reach `retro_run`, did not crash or hang on a rejected load, and the environment-callback mechanism — the trickiest plumbing, since it requires the core to call back into JS during otherwise-synchronous native calls — worked correctly on the first corrected attempt. The total implementation is small: three files, roughly 250 lines combined, using one well-established, prebuilt-binary FFI dependency, isolated from the rest of the repository.

### Comparison against the other acquisition paths

| | mGBA Lua (proven, `P05-T001`–`T006`) | BizHawk External Tool (Codex, in progress) | Stock RetroArch/NCI (researched, not built) | Libretro direct host (this spike) |
|---|---|---|---|---|
| Manual step remaining | Load script each session (confirmed unavoidable, upstream "not planned") | None (`--open-ext-tool-dll`) | None (config-file plumbing, no CLI flag) | None once a ROM is loaded — **but ROM loading itself would need to be driven by our own code, not a GUI** |
| Requires a GUI emulator at all | Yes | Yes | Yes | **No** — this is the only path with no GUI application in the loop |
| Toolchain needed | None beyond mGBA itself | .NET/C# build | None | Node + prebuilt FFI binary (no compiler); a native build would need a C toolchain this environment lacks |
| Evidence quality this session | Extensive, live, real ROM (fixture-derived) | Pending Proof 2 | Documented, not run | Extensive up to the ROM-load boundary; blocked past it by ROM availability, not by the architecture |
| Multi-system reach | GBA-only | Wide (core-agnostic API) | Widest (200+ cores) | Wide (core-agnostic API), same ceiling as BizHawk |

The direct-host path is the only one of the four that removes the GUI emulator from the runtime picture entirely — a meaningfully different, and for a future headless/telemetry-focused architecture, more attractive shape than any of the other three. It is not, on this evidence, a replacement for the near-term BizHawk/mGBA work; it is a second, independently-promising direction worth a continued, still-small next increment once a real ROM can close the remaining gap.
