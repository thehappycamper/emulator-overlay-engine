## Objective

Determine empirically whether EOE can directly host the mGBA libretro core and acquire Pokemon Emerald memory through the official libretro API — no RetroArch, no Lua, no emulator GUI automation, no process-memory hooking. **This is a feasibility spike, not the start of a production emulator frontend**, and this task does not claim production readiness regardless of outcome.

## Why This Task Exists

Follow-up to the prior Libretro/RetroArch research turn's recommendation ("a small [experiment] yes — a full prototype... no") and its named smallest-experiment proposal. That research established the mGBA libretro core registers EWRAM/IWRAM at real hardware addresses via `RETRO_ENVIRONMENT_SET_MEMORY_MAPS` (confirmed from mGBA's own `libretro.c` source), but that was a documentation-only finding — this task tests it against a running core.

## Acceptance Criteria

- A real, official, redistributable mGBA libretro core can be dynamically loaded and its `retro_get_system_info()` output captured.
- The full required callback surface (environment, video, audio ×2, input ×2) can be registered and `retro_init()` completed without the core failing or hanging.
- `retro_load_game()` is attempted and its result (success or failure) is captured and handled without crashing, whichever occurs.
- If a game loads successfully: memory descriptors are captured via the environment callback, EWRAM is located, and at least one known Emerald address is read and reported.
- If a game does not load successfully in this environment (expected, given no legally obtainable ROM is available to this agent — see Result): the exact point and reason execution stopped is documented precisely, not glossed over.
- Address-translation logic is unit tested independent of any live core/ROM, against the real mGBA descriptor shape and including nontrivial `select`/`disconnect`/`offset`/bit-collapsing cases, matching RetroArch's own canonical reference algorithm.
- `retro_api_version()` is explicitly called and its result validated against `RETRO_API_VERSION`, not merely available.
- `retro_deinit()` and callback cleanup are attempted deterministically via `try`/`finally` regardless of which path execution took, with each outcome recorded rather than assumed.
- A clear, evidence-based recommendation is produced from one of the four specified options.

## Implementation Notes

**Toolchain constraint:** no C/C++ compiler is available in this environment (confirmed: `gcc`/`g++`/`cl`/`clang`/`cc` all absent). A from-scratch native frontend (`nanoarch`-style) was not possible here. Used Node.js + [`koffi`](https://koffi.dev/) instead — an FFI library shipping prebuilt native bindings, requiring no compiler. This is a deliberate, disclosed dependency scoped **only** to this isolated experiment directory (its own `package.json`, not referenced by the root `package.json`); it adds nothing to the production dependency tree. `koffi`'s exact API (`koffi.proto`/`koffi.register`/`koffi.struct`/`koffi.decode`/`koffi.view`) was verified against its live documentation and its actual installed behavior, not assumed — an initial attempt using a different (and, it turned out, non-current) API shape (`koffi.callback`) failed immediately and was corrected before proceeding.

**Core source:** the official mGBA libretro core nightly build was downloaded directly from `buildbot.libretro.com` for local testing (not committed to the repository) — this is the libretro project's own official, MPL-2.0-licensed, redistributable emulator core binary, the same category of artifact as installing mGBA or BizHawk itself, containing no game content.

**ABI details** (field layouts, environment command numbers, calling convention) were transcribed from the authoritative `libretro.h` header (RetroArch master branch), not inferred, with each struct/constant in `libretro-abi.mjs` citing what it was checked against.

**Address translation semantics (corrected after independent review):** the original implementation's `select`/`disconnect` handling was self-derived from a plain reading of `libretro.h`'s doc comment, not from a canonical reference implementation, and independent review correctly flagged it as not matching real RetroArch frontend behavior. It has been replaced with a direct transcription of RetroArch's own reference algorithm, `rc_libretro_memory_get_descriptor()` in `deps/rcheevos/src/rc_libretro.c` (RetroArch master branch) — the actual production code the RetroArch frontend uses to translate `retro_memory_descriptor` arrays into readable addresses for its achievements/cheats subsystem, and the most concrete available definition of "RetroArch frontend behavior" for this exact problem. Two corrections resulted:

1. **`select === 0` must not consult `disconnect` at all.** `libretro.h` documents a zero `select` as meaning `start`/`len` are "the complete mapping for this region of memory (i.e. each byte is mapped exactly once)" — no mirroring is possible in that case, so `disconnect` is irrelevant. The reference implementation's `select === 0` branch is a plain range check with no `disconnect` handling whatsoever; the module now matches this exactly, and a test (`zero-select descriptors ignore disconnect entirely...`) pins this behavior down explicitly, including for the atypical (non-real-world, but worth pinning) combination of `select: 0` with a non-zero `disconnect`.
2. **`disconnect` bits must be *collapsed*, not merely zeroed.** The previous `relative & ~descriptor.disconnect` left gaps in the numeric value instead of closing them — correct only by coincidence for a single isolated disconnect bit, and wrong for any real multi-bit bank-mirroring descriptor (it would produce a sparse, usually out-of-bounds offset instead of a compact one). The reference implementation instead repeatedly peels off the lowest set bit of the disconnect mask and shifts the remaining higher bits down to close the gap (RetroArch's own comment credits this to its `mmap_reduce` function). `collapseDisconnectBits()` is a direct transcription of that loop. Additionally, the reference implementation treats "select matches, but the collapsed offset still exceeds `len`" as **no match** (falls through to the next descriptor), which is a real, load-bearing part of correctness that cannot be expressed if matching and offset computation are separate steps — the module now resolves both together internally (`resolveOffsetWithinDescriptor`) for exactly this reason.

Both corrections are backed by hand-derived, independently bit-verified test cases (not just re-running the implementation against itself) in `test/address-translate.test.js`, including a non-adjacent multi-bit disconnect mask (bits 1 and 5) to exercise the collapse loop beyond the trivial single-bit or adjacent-bits case.

**Real mGBA descriptor shape correction:** the prior test suite's EWRAM/IWRAM stand-in descriptors used `select: 0`, which is **not** what the real core registers. Confirmed against mGBA's actual `src/platform/libretro/libretro.c` (`_setupMaps()`, GBA branch): both EWRAM and IWRAM are registered with `select: 0xFF000000` (only the top address byte selects the region — the low 24 bits index directly into the buffer, bounded by `len`) and `disconnect: 0`. The old `select: 0` tests were therefore exercising a materially different code path (the zero-select branch) than what actually runs against the real core (the non-zero-select branch). All descriptor-shaped tests now use the real `select: 0xFF000000` values, and a dedicated test confirms an address with the right top byte but an out-of-range low-24-bit offset (e.g. `0x02040000`, beyond EWRAM's real 256 KiB) is correctly rejected rather than falsely matched.

**`decodeMemoryMap()` dropped `descriptor.offset`:** a second real bug found during the fix pass — the FFI decode step in `libretro-abi.mjs` copied every `retro_memory_descriptor` field into its plain-JS-object return value except `offset`, silently discarding it. `libretro.h` documents `offset` as the field address calculations should use in preference to pointer arithmetic; a dropped `offset` would have produced silently wrong buffer reads for any descriptor with a non-zero offset (real cores use this for regions sharing a backing pointer, e.g. mirrored ROM banks), while looking correct for the zero-offset case this spike's original ad hoc smoke test happened to exercise. Fixed, and regression-tested with a real `koffi` struct encode/decode round-trip (`test/libretro-abi.test.js`), not just a code read — including a case asserting a *zero* offset survives as `0`, not as `undefined`.

**`retro_api_version()` now explicitly called and validated.** `host.mjs` calls it immediately after loading the core, before any other ABI call, compares it against `RETRO_API_VERSION` (`1`, newly exported from `libretro-abi.mjs`), and records both the actual value and the match result in the printed report. Re-run against the real core: `1 === 1`, matches.

**Deterministic cleanup added via `try`/`finally`.** `host.mjs`'s `retro_init`/`retro_load_game`/`retro_run` sequence is now wrapped in a single `try`/`finally` that always attempts `retro_unload_game()` (if a game loaded), `retro_deinit()` (if `retro_init()` was reached), and `koffi.unregister()` for every registered callback — regardless of which path the `try` block took (early return on ROM rejection, full success, or a thrown error) — with every step's outcome recorded in the report rather than assumed. See `README.md`'s "Process exit and koffi callback cleanup" section for a real, disclosed, environment-specific finding surfaced while implementing this: an isolated minimal repro (register a callback that is never invoked by native code, then exit) segfaulted 100% reproducibly (5/5 runs, both Node v20.20.2 and v24.15.0) in this environment, but this spike's actual usage — every callback genuinely invoked by native code before teardown — does not exhibit this; five consecutive full re-runs against the real core all exited `0` with `6/6` callbacks cleanly unregistered.

**Root `npm test` dependency safety.** The new `test/libretro-abi.test.js` imports `koffi`, unlike the pre-existing `test/address-translate.test.js`. Because Node's default recursive test discovery picks up every `*.test.js` file from the repository root regardless of which `package.json` "owns" it, this file guards its own `koffi` import and degrades to a single, clearly-labeled skipped test (rather than throwing and failing the entire root suite) when `koffi` is not resolvable — verified both ways: present (3 real assertions run) and absent via a simulated fresh clone (root `npm test` still exits `0`, with exactly one skipped test named to explain why).

**Save-state consideration:** as anticipated by the task, directly loading the project's existing mGBA `.ss0` savestate into the libretro core was considered and explicitly **not attempted**. libretro's `retro_serialize`/`retro_unserialize` is a core-private opaque blob with no documented guarantee of byte-compatibility with standalone mGBA's own savestate file format, even though both wrap libmgba — forcing compatibility would be exactly the kind of hack this task was told to avoid. This remains an open question requiring either the libretro core producing its own savestate after manual play, or a scoped, separately-approved investigation. Not a blocker for this spike, which read memory after a fixed frame count from power-on instead.

## Result — what was and was not empirically verified

This task record was corrected after independent review found real defects in
the original implementation (dropped `descriptor.offset`, an incorrect
`select`/`disconnect` algorithm not matching RetroArch's own reference
behavior, tests built on an inaccurate EWRAM/IWRAM descriptor shape, no
`retro_api_version()` validation, no deterministic cleanup). All of the below
reflects the **corrected** code, re-verified against a freshly re-downloaded
copy of the real official mGBA libretro core, not the original (partially
incorrect) run.

**Verified, against the real official mGBA libretro core, via the actual committed code (not just exploratory scratch scripts), across 5 consecutive fresh runs:**

- `retro_api_version()` → `1`, explicitly compared against `RETRO_API_VERSION` (`1`) and recorded as a match — not merely called and ignored.
- `retro_get_system_info()` → `{ library_name: "mGBA", library_version: "0.11-219-e31759b", valid_extensions: "gba|gb|gbc|sgb", need_fullpath: false, block_extract: false }` — a real, live-decoded struct via an out-parameter, not a guess; identical across all 5 re-runs (same nightly build).
- Full callback registration (environment, video, audio, audio-batch, input-poll, input-state) succeeded; `retro_init()` completed cleanly.
- The environment callback correctly intercepted **9 real commands** the core issued during init, decoded against `libretro.h`'s exact numeric values: `GET_VFS_INTERFACE` (×2), `GET_CORE_OPTIONS_VERSION`, `SET_VARIABLES`, `SET_PIXEL_FORMAT`, `SET_INPUT_DESCRIPTORS`, `GET_INPUT_BITMASKS`, `GET_VARIABLE`, `GET_LOG_INTERFACE`. All were declined (`false`) with no crash, hang, or misbehavior — confirming the core tolerates a minimal/stub environment implementation for reaching this point.
- `retro_load_game()`, attempted with a 310,356-byte non-ROM file (this repository's own downloaded `libretro.h` copy, used only as a "clearly not a valid GBA ROM" negative-test input — never anything resembling real game content), correctly and safely returned `false`. No crash, no hang.
- **Deterministic cleanup**, exercised on every run regardless of the ROM-rejection early exit: `retro_deinit()` reported `"ok"` and `koffi.unregister()` reported `6/6` callbacks released with zero errors, all 5/5 runs. Process exit code was `0` every time. (`retro_unload_game()` was correctly *not* attempted, since no game ever loaded to unload — recorded as `"not attempted"`, not silently skipped.)
- Pure address-translation logic: 12/12 tests passing against the real mGBA EWRAM/IWRAM descriptor shape (`select: 0xFF000000`, not the previous, inaccurate `select: 0` stand-in), including hand-derived-and-independently-bit-verified nontrivial multi-bit disconnect-collapse cases.
- `decodeMemoryMap()`'s FFI decode path: 3/3 tests passing via real `koffi` struct encode/decode round-trips, confirming `offset` now survives decode (including the zero-offset case, which must decode to `0`, not `undefined`).

**Not verified — blocked on one specific, well-understood cause, unchanged by this fix pass:** no legally obtainable Pokemon Emerald ROM is available to this agent in this environment. `SET_MEMORY_MAPS` is (correctly, per libretro convention) only published by the core after a *successful* game load, which never occurred here or in the original run. Consequently, **still not observed live**: real memory descriptors, EWRAM's actual published start/length, an actual byte value read from a known address, stability of that value across repeated `retro_run()` calls, or CPU/performance characteristics under real execution. The claim that our existing address constants resolve correctly against mGBA's real EWRAM descriptor now rests on: (a) structural confirmation from mGBA's own `libretro.c` source (both the descriptor registration and, newly, the exact `select`/`disconnect` values it uses), and (b) this task's corrected, canonically-algorithm-matching, hand-verified translation logic — still not a live read. This mirrors, in every material respect, the "manual mGBA GUI smoke test remains pending" pattern already established and accepted across every prior `P05` task in this phase, and this fix pass does not claim otherwise: it makes the branch correct and ready for that real-ROM test, not a substitute for it.

## Decision

**LIBRETRO DIRECT HOST IS PROMISING — continue prototype**, with the explicit caveat that the one remaining unproven claim (a real value read from real emulated memory) requires an operator-supplied, legally obtained ROM to close — the same category of gap every other `P05` acquisition task in this phase has carried at this stage, not a new or worse one.

Every failure mode this spike could plausibly have hit did not occur: the core did not require a compiler to interoperate with (a real concern going in, given this environment has none), did not require real video/audio/input to reach `retro_run`, did not crash or hang on a rejected load, and the environment-callback mechanism — the trickiest plumbing, since it requires the core to call back into JS during otherwise-synchronous native calls — worked correctly on the first corrected attempt. The total implementation is small: three files, roughly 250 lines combined, using one well-established, prebuilt-binary FFI dependency, isolated from the rest of the repository.

### Comparison against the other acquisition paths

| | mGBA Lua (proven, `P05-T001`–`T006`) | BizHawk External Tool (Codex, in progress) | Stock RetroArch/NCI (researched, not built) | Libretro direct host (this spike) |
|---|---|---|---|---|
| Manual step remaining | Load script each session (confirmed unavoidable, upstream "not planned") | None (`--open-ext-tool-dll`) | None (config-file plumbing, no CLI flag) | None once a ROM is loaded — **but ROM loading itself would need to be driven by our own code, not a GUI** |
| Requires a GUI emulator at all | Yes | Yes | Yes | **No** — this is the only path with no GUI application in the loop |
| Toolchain needed | None beyond mGBA itself | .NET/C# build | None | Node + prebuilt FFI binary (no compiler); a native build would need a C toolchain this environment lacks |
| Evidence quality this session | Extensive, live, real ROM (fixture-derived) | Pending Proof 2 | Documented, not run | Extensive up to the ROM-load boundary; blocked past it by ROM availability, not by the architecture |
| Multi-system reach | GBA-only | Wide (core-agnostic API) | Widest (200+ cores) | Wide (core-agnostic API), same ceiling as BizHawk |

The direct-host path is the only one of the four that removes the GUI emulator from the runtime picture entirely — a meaningfully different, and for a future headless/telemetry-focused architecture, more attractive shape than any of the other three. It is not, on this evidence, a replacement for the near-term BizHawk/mGBA work; it is a second, independently-promising direction worth a continued, still-small next increment once a real ROM can close the remaining gap.
