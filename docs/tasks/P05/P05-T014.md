## Objective

Connect the merged, isolated Libretro IPC provider (`P05-T013`) to the existing, provider-neutral Pokemon Emerald acquisition pipeline (`adapters/pokemon-emerald-us-rev0/`) via a thin adapter, proving `EOE parent -> Libretro provider child -> official mGBA core -> generic memory reads -> thin Libretro Emerald adapter -> existing acquisition/mapping/normalized state` end to end.

## Why This Task Exists

`P05-T013`'s own follow-up: "Provider-neutral Libretro source snapshot adapter after this IPC boundary is reviewed." See [ADR 0028](../../decisions/0028-libretro-emerald-thin-adapter.md).

## Dependencies

`P05-T013` (isolated Libretro provider IPC) complete and merged on `origin/main`.

## Scope

- New adapter package `adapters/libretro-emerald/`: `reader.js` (region resolution + bounded snapshot fetch + synchronous reader), `identity.js` (file-hash-based ROM identity), `acquire.js` (orchestration), `extension.json`, `README.md`.
- `LIBRETRO_SOURCE` provenance descriptor added to the existing `adapters/pokemon-emerald-us-rev0/emerald-source-contract.js`, alongside `MGBA_SOURCE`/`BIZHAWK_SOURCE`.
- New bounded, one-shot CLI `tools/proof-libretro-emerald.mjs` (`npm run proof:emerald:libretro`, with a `--check` mode).
- Provider-parity coverage extended to a third provider (Libretro), comparing normalized state against mGBA and BizHawk.

## Non-Goals

Input injection, savestates, memory writes, controller UI, audio/video output, core downloading/updating, achievements/netplay, and a full Libretro frontend. No Emerald memory address, Gen III struct decoding, or species/move/item/location lookup logic was added to `experiments/libretro-provider/` or duplicated anywhere in this adapter - all of it is reused, unmodified, from `adapters/pokemon-emerald-us-rev0/`. Does not duplicate `P05-T012`'s session orchestrator and does not make Libretro a production-default provider.

## Acceptance Criteria

- `experiments/libretro-provider/` (the isolated provider) is unmodified and remains fully generic.
- `readEmeraldAcquisition`, the decryption/lookup logic, and `assertSupportedEmeraldIdentity` in `adapters/pokemon-emerald-us-rev0/` are called, not reimplemented or modified.
- A synchronous `{read8, read16, read32}` reader, backed by bounded Libretro `readRange` IPC calls, produces byte-identical acquisition output to the existing canonical fixture.
- The adapter fails closed on: unsupported ROM identity, unsupported Libretro core, and a memory map missing a verified region - before any acquisition is attempted in each case.
- A full pipeline run (fixture-backed) produces a schema-valid Emerald source snapshot with `LIBRETRO_SOURCE` provenance, maps through the existing, unmodified mapping to valid Pokemon overlay state, and matches mGBA/BizHawk output exactly except for provenance.
- The provider is always shut down, on success or on any failure path.
- A real end-to-end smoke against the official mGBA core and a real, legally-owned Emerald ROM completes without error.

## Implementation Notes

**The sync/async bridge is the one genuinely new problem.** `readEmeraldAcquisition(reader)` calls `reader.read8/16/32(address)` synchronously, dozens of times per acquisition (once per Pokemon field, across up to seven Pokemon). Libretro IPC is a child-process round trip per request. Rather than one IPC call per field (slow, and architecturally incompatible with a synchronous reader anyway), `reader.js` fetches exactly one bounded snapshot per verified GBA domain - EWRAM (`0x02000000`/`0x40000`) and IWRAM (`0x03000000`/`0x8000`), the same two domains BizHawk's own `gba-memory-domains.js` already claims - via two `readRange` calls (run concurrently; both comfortably fit under the provider's 1 MiB bound), then hands `readEmeraldAcquisition` a synchronous reader backed by those already-fetched `Buffer`s. No IPC occurs during decoding itself.

**Region resolution, not hardcoded region IDs.** `resolveVerifiedRegions()` scans the Libretro provider's own discovered `memoryRegions` (from its `initialize` response) for whichever region *contains* each verified GBA domain by address range, rather than assuming a fixed region index/ID - the real official mGBA core's region ordering was independently confirmed via manual real-core inspection but is not trusted to stay stable, and this function fails closed (`LibretroEmeraldMemoryMapError`) if a domain is missing, too small, or marked inaccessible.

**Identity by file hash, not memory read-back.** Unlike mGBA's Lua API (`emu:getGameCode()`/`emu:getGameTitle()`), the Libretro provider exposes no high-level identity call - only low-level memory regions. `identity.js` computes CRC32 directly from the local ROM file (via `node:zlib`'s `crc32`, independently verified against the real Emerald ROM: computed `1F1C08FB`, matching the known value exactly) before the provider is ever asked to load it, so a wrong ROM fails closed without spending a core-load round trip on content that would be rejected anyway. `gameCode`/`title`/`revision` are not independently re-read from the ROM header - a CRC32 match against the known-good hash already proves the file is byte-for-byte identical to the reviewed ROM, making a separate header re-read redundant; this mirrors BizHawk's own established pattern of trusting the shared identity constant once a whole-ROM hash matches, rather than inventing a new verification strategy. `computeEmeraldRomIdentityFromBytes` reports what was found; `assertSupportedEmeraldIdentity` (the existing, unmodified function) remains the sole authority on whether it is accepted.

**Direct JS reuse, no Lua port.** Unlike mGBA/BizHawk (Lua-scripted emulators requiring a hand-ported `emerald-acquisition.lua` copy of the decode logic), the Libretro provider is a genuine Node.js child process reachable by the parent's own JS - `acquire.js` calls the canonical `readEmeraldAcquisition` directly. This is a structurally better integration path than the two existing providers have, not a compromise.

**Fail-closed pipeline order.** `acquireEmeraldSourceSnapshot()` checks ROM identity *before* calling the provider's `initialize`, and the Libretro core's identity *before* any memory read - each gate is proven, by test, to short-circuit before the next stage's expensive/risky work runs (no `initialize` call on a wrong ROM; no memory read on an unsupported core).

**Cleanup is unconditional.** `runOnceEmeraldLibretroAcquisition()` wraps acquisition in try/finally, calling `client.shutdown()` regardless of where in the pipeline a failure occurred (identity, core, region resolution, or an unexpected provider error) - proven for every one of those failure points individually, not just the success path.

**Real end-to-end smoke.** Using the real official mGBA core and a real, legally-owned Emerald ROM (per `experiments/libretro-provider/README.md`'s documented local-experiment convention, not committed), `npm run proof:emerald:libretro -- --check` and the real run both completed successfully, producing a schema-valid source snapshot and mapped state with correct `libretro`/`"Libretro (mGBA core)"` provenance throughout. The acquired party is empty and no battle is active - correctly and honestly, since neither the isolated Libretro provider nor this adapter can load a savestate (out of scope for both), so a freshly-booted ROM with no save file has no in-game party to observe. This is the same class of disclosed limitation prior `P05` tasks have already carried for real-ROM acceptance testing, not a defect in this adapter.

## Security/Compatibility Considerations

No ROM, BIOS, save, or core binary is committed. No new arbitrary-code-execution path: this adapter only calls existing, already-reviewed functions (`readEmeraldAcquisition`, `assertSupportedEmeraldIdentity`, `readValidatedEmeraldSourceSnapshot`) and the existing, already-reviewed generic Libretro provider's own IPC operations - no new dynamic evaluation surface. Additive-only: `emerald-source-contract.js` gained one new exported constant; no existing schema, mapping, or provider's behavior changed. Identity verification (CRC32 of the local ROM file) happens before any content is handed to the provider for loading, so a misconfigured or wrong ROM is rejected before it is ever executed by the mGBA core.
