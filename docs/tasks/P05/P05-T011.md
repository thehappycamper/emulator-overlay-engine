## Objective

Show the current location's wild encounter rates, and - only during an active wild battle - the player's Poke Ball inventory alongside a live, state-aware catch-probability estimate for the current opponent (reflecting its actual current HP and status, not a static per-species number).

## Scope

- New game-owned reference data: `data/encounters.{json,lua}` (per-location wild encounter slots, from `pret/pokeemerald`'s own `src/data/wild_encounters.json`) and `data/balls.{json,lua}` (the 12 Gen III Poke Ball types' catch-multiplier rules, transcribed from `pret/pokeemerald`'s real `Cmd_handleballthrow`).
- New acquisition decoding: the save block's Poke Ball pocket (`bagPocket_PokeBalls`, 16 slots), each species' base `catchRate`, and `battle.trainerBattle` (from the already-decoded `typeFlags` word's `BATTLE_TYPE_TRAINER` bit).
- New pure formula functions in `reference-data.js`: `resolveBallMultiplier` and `calculateCatchChance`, both transcribed directly from the real Gen III catch algorithm, called from the acquisition layer (not presentation - see [ADR 0022](../../decisions/0022-encounter-rates-and-catch-odds.md) for why that boundary matters).
- Two new collapsed-by-default presentation panels: "Wild Encounters Here" (always available when location data exists) and "Poke Balls" (only during an explicitly wild, non-trainer battle).
- Smallest-principled schema/mapping extension: `pokemon.catchRate`, `battle.trainerBattle`, `bagItem.catchChance` are new; `location.encounters` and top-level `bag` were already present in the target schema from before `P05-T009` and are simply populated with real data again.

## Non-Goals

- Dive Ball, Repeat Ball, Timer Ball, and Safari Ball catch multipliers - each depends on state this project does not decode (underwater map-type, per-species Pokedex "caught" flag, battle turn counter, Safari catch factor respectively); each is marked `unavailable` with a disclosed reason in `balls.json`, never given a guessed value.
- Any bag pocket other than Poke Balls (general items, key items, TMs, berries).
- Any UI or mechanism to actually throw a ball or take a battle action - read-only display only, consistent with this project's existing scope guard.
- Battle stat comparison / stat stages - that is `P05-T010`, a separate, parallel task this branch does not depend on or include.

## Implementation Notes

**Wild encounter table.** `pret/pokeemerald`'s `src/data/wild_encounters.json` is already valid JSON (not C source needing regex parsing), fetched via `gh api` and parsed directly. Its `MAP_<CONST>` symbolic map names are correlated to `(mapGroup, mapNumber)` pairs by re-deriving each real map folder name's `MAP_<UPPER_SNAKE>` constant form from `data/maps/map_groups.json` (the same source `locations.json` used in `P05-T009`) and matching by exact string equality - mechanical, not guessed. 81 of the ROM's maps have a standard wild encounter table; the rest (towns, buildings, etc.) correctly have none.

**Poke Ball pocket offset.** `struct SaveBlock1`'s `bagPocket_PokeBalls` field is annotated at byte offset `0x650` directly in `pret/pokeemerald`'s `include/global.h` (the same explicit-offset-comment convention already trusted for `flags`/badges in `P05-T009`); the next field (`bagPocket_TMHM`) starts at `0x690`, giving `(0x690-0x650)/4 = 16` four-byte `ItemSlot{u16 itemId; u16 quantity;}` entries - confirmed by that same struct's own field definition, not assumed.

**Catch-rate formula.** Transcribed field-for-field from the real `Cmd_handleballthrow` (`src/battle_script_commands.c`), including the exact `sBallCatchBonuses` table and every ball's real conditional-multiplier logic (Net Ball's type check, Nest Ball's level scaling). The shake-probability tail (`Sqrt(Sqrt(16711680/odds))` then `1048560/b`, four independent `Random() < threshold` checks) is reproduced as a closed-form `(threshold/65536)^4` using `Math.sqrt`/`Math.floor` rather than simulated RNG - a disclosed floating-point re-implementation of the same integer formula, sanity-checked against a well-known reference case (catchRate 45, Poke Ball, full HP, no status -> odds 15/255, ~6.1% catch chance, matching widely-cited community figures for that exact scenario).

**Master Ball.** The visible portion of `Cmd_handleballthrow` indexes `sBallCatchBonuses[gLastUsedItem - ITEM_ULTRA_BALL]` for every non-"special" ball, but Master Ball's item ID (1) is *lower* than Ultra Ball's (2), so that expression would underflow for Master Ball specifically - meaning its real multiplier resolution happens somewhere this task's source excerpt didn't show (very likely a distinct battle-script path for that specific ball, not the general multiplier table at all). Rather than guess at unseen code, Master Ball is handled here as an unconditional guaranteed catch - well-established, undisputed Pokemon game knowledge independent of the specific implementation detail.

**Architecture boundary.** `resolveBallMultiplier`/`calculateCatchChance` live in the game-owned `reference-data.js` and are invoked from `readEmeraldAcquisition()`, not from presentation - `catchChance` arrives at the presentation layer as an already-computed number (or `null`), the same pattern already used for `expProgress`/`status`/`gender`. `src/domains/pokemon/presentation.js` contains no Emerald-specific formula.

**Wild-only gating, strict.** The "Poke Balls" panel checks `state.battle.trainerBattle === false` explicitly, not `!== true` - an absent/unknown `trainerBattle` value must never be treated as "confirmed wild," since showing ball-throw odds during an actual trainer battle would be actively misleading (the player cannot throw balls there at all). The acquisition layer always computes this field explicitly (never leaves it undefined), so this stricter check costs nothing in the real pipeline.

**Fixture regeneration discipline.** `emerald-us-rev0-derived.json` (a richer fixture than its name suggests - it holds both a raw memory-address map AND the expected fully-decoded output, used to cross-verify the real decoder end-to-end) was initially clobbered by mistake with the wrong content during this task and was restored from git history, then correctly patched (new Poke Ball memory addresses, `catchRate`/`trainerBattle`/`bag`/`encounters` expected values) and re-verified via the existing `readValidatedEmeraldSourceSnapshot`-vs-fixture equality test. `emerald-us-rev0.source.json` was then regenerated *from* that corrected memory map through the real `readEmeraldAcquisition`/`createEmeraldSourceSnapshot` functions, so the two fixtures are provably consistent with each other and with the real decoder, not just hand-edited to look right.

**Lua port.** `emerald-acquisition.lua` was extended field-for-field to mirror every JS change (bag pocket read, `catchRate`, `trainerBattle`, `resolveBallMultiplier`/`calculateCatchChance`, JSON serialization for the new fields), loading the two new `data/{encounters,balls}.lua` tables the same way it already loads the five existing ones. **This port has not been executed** - no Lua interpreter is available in this development environment - and is verified only by manual review and a brace/paren-balance check (59/59 braces, 289/289 parens), consistent with the same disclosed limitation `P05-T009` already carries for this module, which real BizHawk acceptance testing during `P05-T009`'s review has already begun narrowing (a connector smoke test, not yet exercising this task's additions).

## Tests Required

- `resolveBallMultiplier`: static balls return their fixed multiplier; Net Ball's type-conditional bonus; Nest Ball's level-scaling formula (including the level-40+ and floor-at-10 edges); every "unavailable" ball returns `null`, never a guessed number.
- `calculateCatchChance`: matches a known reference case (~6% for a base catchRate-45 species, Poke Ball, full HP, no status); Master Ball is always 1 (guaranteed); lower HP and status conditions increase the computed chance (directionally correct); missing/unusable inputs (`null` catchRate/multiplier/HP) return `null`, never a fabricated number.
- `lookupEncounters`/`lookupBallInfo`: resolve real data (Route 101's real Wurmple/Poochyena/Zigzagoon table; the real Poke Ball reference table) and return `null` for anything unresolvable.
- Presentation: wild-encounter panel collapsed by default, lists the real table, shows an explicit "no wild encounters" message (not an empty table) for locations without one; ball panel renders only when `trainerBattle === false` explicitly (not merely "not `true`" - a dedicated test proves an *unknown* `trainerBattle` value also hides the panel); ball panel never renders outside of battle even with balls in the bag; a computed percent and an honest "unavailable" marker both render correctly; HTML-significant ball names are escaped (renderer-safety regression test).
- Full acquisition/mapping/schema round-trip: the real fixture's Poke Ball inventory and computed `catchChance` values flow end-to-end from raw memory bytes through decoding, the source contract, the mapping, and target schema validation.

## Security/Compatibility Considerations

No ROM, save, or copyrighted asset is included - `encounters.json`/`balls.json` are name/metadata/formula tables mechanically generated from the MIT-licensed `pret/pokeemerald` project's own source, the same category of data as `P05-T009`'s existing tables. All new user-influenced strings (ball names, encounter species names) pass through the existing `escapeHtml` helper - proven by dedicated XSS-style regression tests. Schema changes are additive/backward-compatible: `catchRate` and `catchChance` are new optional/nullable fields, and `trainerBattle` is a new required field the acquisition layer always populates, so nothing that validated under the prior schema stops validating once regenerated through the real pipeline.
