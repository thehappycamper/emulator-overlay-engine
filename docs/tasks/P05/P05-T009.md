## Objective

Turn the current Proof 2 Pokemon overlay - one fixed party slot, one opponent, and literal placeholder text for names/types/moves - into a genuinely useful live team/battle dashboard: the whole player team, real per-member detail, a separate battle panel, and real resolved Emerald names wherever the acquisition layer can actually decode them, working identically for mGBA and BizHawk through the existing provider-neutral pipeline.

## Why This Task Exists

`P06-T002` gave both emulator providers a shared, validated acquisition contract, but nothing downstream used more than the first party slot or replaced any of ADR 0019's original placeholder text. ADR 0019 explicitly named this as expected future work ("Species/move/map lookup data can replace placeholders in later mapping/data tasks without redesigning acquisition"). This task is that follow-up, scoped as its own governance task per direction to allocate the next appropriate task ID from `origin/main` and avoid the concurrently-in-progress Libretro experimental area (`P05-T007`).

## Scope

- Decode every occupied party slot (not one fixed slot) - nickname, species, level, gender, current/max HP, status, held item, EXP and progress-to-next-level, individual stats/IVs, and moves with current/max PP.
- Decode the same detail for the active battle opponent when a battle is active.
- Resolve species/move/item names, move type/category/power/accuracy, and the current map's human-readable location name through a new static reference-data layer, generated from real `pret/pokeemerald` source rather than typed from memory.
- Decode badge progression (8 badges) from the save block.
- Redesign `src/domains/pokemon/presentation.js`/`.css` into a compact six-slot team grid plus a separate battle panel; render unoccupied slots intentionally rather than omitting or faking them.
- Extend the source schema, target schema, and mapping project as the smallest principled change needed to carry the above (see [ADR 0021](../../decisions/0021-emerald-live-dashboard-and-reference-data.md) for the full compatibility-impact rationale).
- Port the same decode/lookup logic into the one shared Lua acquisition module (`adapters/pokemon-emerald-us-rev0/emerald-acquisition.lua`) so both mGBA and BizHawk gain this identically, with no provider-specific game-semantics branch in either thin connector.

## Non-Goals

Per explicit instruction, this task does **not** add: events/rules/permadeath enforcement, actions/input control, multiplayer, Libretro production integration, full inventory/bag beyond the single held item already shown per Pokemon, or an overlay builder/editor. It also does not implement: battle stat-stage decoding, opponent battler-switch-index tracking (which specific opposing slot is currently active in a double battle), route encounter tables, catch-rate/catch-odds display, or the prior header's seed/frame/score meters - none of these have a data source in the current acquisition layer, and per the "do not fake unavailable values" instruction they are dropped rather than shown as placeholders. TM move numbers/held-item full bag contents beyond one held item remain out of scope. It does not touch `P05-T007`'s Libretro spike or `P05-T008`'s memory explorer (separate branches).

## Developer Tool Built First (P05-T008)

Per an explicit mid-task instruction, a small developer-only live memory/data explorer was evaluated for whether it would materially accelerate this work. Its scope (raw memory inspection UI, typed hex interpretation, watch diffing, comparison against provider-neutral and Pokemon-normalized values) was substantial enough to meet the instruction's own stated condition for splitting it into a separate task, so it was implemented and pushed as `P05-T008` on `feat/P05-T008-emerald-memory-explorer` and is not part of this branch. Because no live emulator/ROM is available in this development environment, this task ultimately relied on authoritative upstream source research (`gh api` against `pret/pokeemerald`) rather than the explorer itself to enrich the dashboard - the explorer remains available for a real acceptance session to use interactively.

## Implementation Notes

**Reference data provenance.** `adapters/pokemon-emerald-us-rev0/data/{species,moves,items,locations,charmap}.{json,lua}` were generated from real `pret/pokeemerald` master-branch source fetched via `gh api repos/pret/pokeemerald/contents/<path>?ref=master` (raw base64 content, not WebFetch's summarizing model, which cannot reliably extract large exact tables) and parsed with plain Node.js regex/brace-matching. See `data/README.md` for the exact source file per table. Spot-checked against known facts: Bulbasaur is Grass/Poison; Torchic is pure Fire; Tackle is 35 power / 95 accuracy / 35 PP in Gen III.

**Encrypted substruct decoding.** The existing `GROWTH_SUBSTRUCT_INDEX` table (proven correct in `P05-T004`) and the three sibling 24-entry order tables (Attacks, EVs/Condition, Misc) were all cross-verified against the same real `SUBSTRUCT_CASE` table in `pokeemerald/src/pokemon.c`'s `GetSubstruct()`, not derived independently. Move category (physical/special) is derived from type via the documented Gen I-III rule (`type < TYPE_MYSTERY` is physical, `type > TYPE_MYSTERY` is special; Gen III does not store category per move). Gender is derived from `genderRatio` and the low byte of `personality` per `pokemon.c`'s `GetGenderFromSpeciesAndPersonality`. PP-with-bonus uses the real `CalculatePPWithBonus` formula. EXP-to-next-level progress uses the six real growth-rate formulas from `experience_tables.h`, clamped so it is never fabricated past level 100 and returns `null` rather than a guessed number when the source's growth rate or exp value is unusable.

**Verification without a live emulator.** No ROM or running emulator is available in this environment. A standalone fixture encoder (a second, independently-reasoned implementation of the encryption/packing logic, not sharing code with the decoder under test) produced realistic encrypted memory-read fixtures for a two-member party (TORCHIC/"SPROUT" and a fainted, asleep BULBASAUR/"SLEEPY") and a CHARIZARD opponent, which were round-tripped through the real `decodeGen3Pokemon`/`readEmeraldAcquisition`/mapping/schema-validation/rendering pipeline end-to-end. This is genuine, non-tautological verification: the encoder and decoder are separate code paths reasoned independently from the same struct-layout facts.

**Schema evolution.** Made as the smallest principled change rather than a redesign: `move`'s required fields loosened from five to two (`id`, `name`); `name`/`types`/`item` made nullable; new fields (`gender`, `exp`, `expProgress`, `currentPp`, `maxPp`, `badges`) added as optional/nullable rather than replacing anything. Full compatibility-impact rationale is in [ADR 0021](../../decisions/0021-emerald-live-dashboard-and-reference-data.md).

**Mapping scale.** The mapping engine's field-copy already deep-clones nested JSON values, so per-Pokemon `stats`/`ivs`/`moves`/`types`/`expProgress` are each copied with one whole-object/array field mapping rather than flattening every leaf field, keeping the regenerated mapping (132 field mappings for 6 party slots + opponent) manageable and machine-generated rather than 40+ hand-duplicated entries per slot.

**Fallback behavior, not fabrication.** `location.name` falls back to the literal string `"Unknown location"` (not a real place name) only when the save block region is genuinely unreadable; `player.badges` is omitted (`null`) rather than forced to an all-`false` array in the same case, so "unknown" is never rendered as "none obtained." Two real bugs were caught and fixed by the test suite during development: an empty party previously failed to produce the required `/player/party` key at all (fixed with an explicit default-array placeholder mapping), and an unreadable location previously threw and hid the *entire* overlay state because `location.name` was marked `required: true` (fixed by making it a defaulted, non-required field).

**Lua port is untested.** `emerald-acquisition.lua` (the one shared module both `adapters/gen3-mgba/emerald-acquisition.lua` and `adapters/bizhawk/proof-connector.lua` load) was hand-ported field-for-field from the independently unit-tested JS implementation it mirrors. No Lua interpreter (`lua`, `lua5.1`, `lua5.3`, `lua5.4`, `luajit`) is available in this development environment (confirmed via `which`), so **this port has not been executed**, only reviewed and checked for brace/paren balance. This is a disclosed, named risk, not a claimed proof - see Known Gaps and the BizHawk acceptance checklist below.

## Security/Compatibility Considerations

No ROM, save file, savestate, or copyrighted game asset is included anywhere in this change - the new `data/` tables are name/metadata lookups (species names, move names, location names), the same category of public game-fact data any Pokemon reference tool publishes, mechanically generated from the MIT-licensed `pret/pokeemerald` decompilation project's own source rather than copied game code or media. `decodeGen3Text` stops at the real in-game string terminator byte (`0xFF`) and is bounded by the fixed 10-byte nickname field, so a corrupted/adversarial memory read cannot produce an unbounded string. `escapeHtml` is applied to every user-influenced string (nickname, in particular, since Gen III nicknames are player-settable) before it reaches rendered markup - proven by a dedicated XSS-style regression test. The schema changes are backward-compatible loosenings/additions only (see ADR 0021); nothing that validated under the prior stricter/narrower schema stops validating.
