## Objective

Promote the proven direct-host concept into the first isolated Libretro provider prototype. Native Libretro cores run in a child process while the EOE-side client uses a small versioned local IPC contract.

## Why This Task Exists

P05-T007 proved the direct-host fundamentals with a real Emerald Rev 0 session. The next risk is process isolation and a provider-neutral boundary, not another ABI feasibility experiment.

## Dependencies

P05-T007 completed and operator-verified; P05-T008 remains a separate unmerged memory-explorer branch and is not included.

## Scope

- Child-process native core execution under `experiments/libretro-provider/`.
- JSON-lines protocol for lifecycle, identity, capabilities, memory regions, bounded reads, frame execution, errors, and shutdown.
- Parent client timeout/exit handling.
- Generic memory access only; no Emerald/Pokemon semantics.

## Non-Goals

Writes, savestates, controller input, audio/video presentation, core updater, achievements, netplay, overlay integration, mapping, normalized state, and production frontend behavior.

## Acceptance Criteria

- Native core loading is confined to the child process.
- Normal startup/shutdown and structured lifecycle identity work.
- Child crash, unexpected exit, startup failure, malformed requests, ABI mismatch, out-of-range reads, and timeout behavior are deterministic.
- Memory reads are bounded and region-relative.
- Paths containing spaces cross the IPC boundary without shell interpretation.
- Parent tests remain alive after child failure.

## Implementation Notes

The child reuses the reviewed Libretro ABI declarations and address translation logic, with its own isolated Koffi dependency. A bootstrap frame runs during `initialize` because the official mGBA core publishes its memory map during frame execution. `read16` and `read32` are little-endian; range reads are capped at 1 MiB and returned as base64.

**Blocking finding fix: request serialization.** Independent review found that `provider-child.mjs`'s `input.on("line", async (line) => {...})` dispatched each request as an independent async callback with no serialization: `readline`'s `"line"` event does not wait for a previous async listener's returned promise before firing the next one, so nothing guaranteed one request's full `handle()`+response cycle finished before the next began. Concretely, an `initialize` immediately followed by `run` could interleave and let `run` observe pre-initialization `runtime` state.

Fixed with a new, minimal, dependency-free `request-queue.mjs` (`createSerialQueue()`): a strict promise-chain FIFO queue where every enqueued task's full settlement (success or failure) completes before the next task begins, and a task that throws never blocks, corrupts, or is skipped by later tasks - the queue's own internal chain is always reset to a resolved promise regardless of a task's outcome. `provider-child.mjs` now routes every request (including JSON-parse failures, via `assertRequest` inside `handle()`) through one shared queue instance.

Shutdown is gated by a `shuttingDown` flag set **synchronously the instant a shutdown request is received** on stdin - before it is even enqueued - not once it finishes executing. Shutdown itself still waits its turn in the queue behind any already-arrived work ("shutdown waits for prior work"), but any request arriving after it is rejected immediately and deterministically with a new `PROVIDER_SHUTTING_DOWN` structured error (previously such requests were silently dropped with no response at all, relying on the parent's own request timeout to eventually notice) - it can never be queued behind shutdown or race its teardown of `runtime`.

Request/response ID correlation is unchanged - the queue only serializes *when* each request's handler body runs, not the id-generation/correlation logic already owned by `client.mjs`'s `pending` Map, which was independently re-verified to already correctly handle fragmented JSON-lines input, coalesced multi-message chunks, unexpected/unknown response ids, and corrupted/malformed output lines (all pre-existing, correct behavior - confirmed by new regression tests, not a code change).

## Security/Compatibility Considerations

The child-process boundary limits native crashes and hangs to the provider process, but it is not a full sandbox. IPC is local and unauthenticated. Koffi remains isolated from root production dependencies. No writes or arbitrary code execution are exposed through requests.

## Review Findings

Independent review required because this introduces native child-process execution and a public-facing provider boundary.

**Round 1: one blocking finding.** `provider-child.mjs` dispatched each incoming request as an independent, unserialized async callback (see Implementation Notes) - a real, concrete correctness gap for a lifecycle-sensitive protocol (an `initialize` immediately followed by `run` could race). Fix pushed on `fix/P05-T013-serialize-provider-requests`, scoped strictly to this one finding: a new `request-queue.mjs` primitive, its wiring into `provider-child.mjs`'s dispatch (including a synchronous shutdown-door-closing flag), and regression coverage (unit tests for the queue itself, real-IPC ordering tests against a koffi-free stand-in, a sanity check proving the tests are non-vacuous, and IPC-robustness tests for the parent's stream parsing pinning down already-correct behavior the reviewer separately flagged as non-blocking). No Emerald integration, writes, savestates, input injection, or frontend work was added, per explicit instruction.

**Incidental, necessary fix during the fix pass:** adding new test files (even a single trivial, process-spawn-free file) was found to reproducibly flip a *pre-existing, unrelated* test (`"timeout is surfaced for an unresponsive child"` in `test/provider.test.js`) from passing to failing under the full root `npm test` run - confirmed via a targeted probe (adding one trivial synchronous no-op test file elsewhere in the repository reproduced the same failure) to be a pure Node test-runner file-count/scheduling artifact exposing that test's already-marginal 250ms startup budget, not anything caused by this fix's own logic or by real-process resource contention specifically. Since any task adding test files here would trigger this, and root `npm test` must stay reliably green, that one pre-existing test's `timeoutMs` was widened (250ms → 1500ms, plus an explicit `await client.start()` before the timed request) with no change to what it verifies. Confirmed clean across 6 consecutive full root `npm test` runs after the fix.

Independent re-review of the fix pass remains pending.
