## Objective

Correct Emerald Poke Ball quantity decoding in the shared game-owned acquisition layer and keep the JS/Lua providers behaviorally aligned.

## Why This Task Exists

Raw Emerald `ItemSlot.quantity` values are encrypted with `SaveBlock2.encryptionKey`. Treating them as plaintext produced values above the normalized schema's maximum of 999 during the BizHawk proof. The fix is narrowly scoped to acquisition decoding and fail-closed handling of missing SaveBlock2/key data.

## Dependencies

`P05-T011` bag/Poke Ball acquisition and `P05-T014`'s separately active Libretro adapter task. This task does not depend on or modify the Libretro branch.

## Scope

- Decrypt the Poke Ball pocket's 16-bit raw quantities using the lower 16 bits of the 32-bit SaveBlock2 key.
- Keep `itemId` plaintext and preserve the existing quantity schema bound.
- Make JS and Lua acquisition return `bag: null` when SaveBlock2 or its key cannot be read.
- Correct the public-safe raw-memory fixture and add regression coverage.

## Non-Goals

No normalized-state/schema changes, clamping, broader bag-pocket support, proof-orchestrator changes, events, rules, actions, notifications, or real-ROM acceptance claim.

## Acceptance Criteria

- The fixture's encrypted Poke Ball quantities decode to 8, 3, and 1 while item IDs remain 4, 3, and 2.
- Missing SaveBlock2 pointer or unreadable key produces `bag: null`, never a zero-key fallback.
- Plaintext interpretation of the encrypted fixture quantity is shown to exceed 999 and the corrected value remains schema-valid.
- JS and Lua use the same 16-bit XOR semantics and raw layout.
- Existing downstream mapping and provider parity remain unchanged.

## Implementation Notes

Authoritative `pret/pokeemerald` evidence is recorded in the implementation comments and reviewed for this task: `include/global.h` places `SaveBlock2.encryptionKey` at `0xAC`; `src/item.c` reads and writes `ItemSlot.itemId` directly while applying `GetBagItemQuantity`/`SetBagItemQuantity` to the separate `u16 quantity` field; and `src/load_save.c` carries the SaveBlock2 key through bag save/load handling. The runtime pointer table begins at Emerald's known `gSaveBlock1Ptr` location `0x03005D8C`, with `gSaveBlock2Ptr` at the following 4-byte slot `0x03005D90`.

The JS reader catches unreadable pointer/key reads and leaves unrelated state fields available. The Lua reader uses protected calls for those optional SaveBlock2 reads. Neither path clamps a decoded quantity or substitutes a zero key.

The raw fixture stores `8 ^ 0x1A2B3C4D` low 16 bits (`15429`), `3 ^ key` (`15438`), and `1 ^ key` (`15436`) at the Poke Ball quantity addresses, while item IDs remain plaintext.

## Review Findings

Independent review (fresh, from `f2744ca88fd1da91ae4dcd7a3d70609ff63e6292`, not relying on implementation claims): **APPROVE**.

Verification performed:
- Confirmed against live `pret/pokeemerald` source (`include/global.h`, `src/item.c`, `src/load_save.c`) that `struct ItemSlot { u16 itemId; u16 quantity; }`, `SaveBlock2.encryptionKey` is a `u32` at offset `0xAC`, `gSaveBlock2Ptr` is declared immediately after `gSaveBlock1Ptr` in `load_save.c`, and `GetBagItemQuantity()`/`SetBagItemQuantity()` XOR `quantity` (not `itemId`) against `encryptionKey` uniformly across every bag pocket.
- Independently recomputed the fixture's raw quantities (`15429`, `15438`, `15436`) against key `0x1A2B3C4D` (`& 0xFFFF` = `0x3C4D`) and confirmed they XOR-decode to exactly `8`, `3`, `1`; confirmed item IDs `4`, `3`, `2` are untouched/plaintext; confirmed the undecoded raw value `15429 > 999`, reproducing the real acceptance failure's causal path.
- Reviewed the full JS and Lua diffs line by line: both apply the identical `(rawQuantity ^ (encryptionKey & 0xFFFF)) & 0xFFFF` semantics, decrypt quantity exactly once, never touch `itemId`, and gate `bag` on `saveBlock1Readable && saveBlock2Readable` (fail-closed, no zero-key fallback, no clamping).
- Adversarially mutated a local copy of `emerald-us-rev0.js` (reviewer-only, not committed) to (a) drop the XOR decryption and (b) drop the SaveBlock2 readability gate; confirmed the committed regressions fail in both cases, then restored the file and confirmed `git diff` was clean and `npm test` passed again.
- Audited both fixtures: `emerald-us-rev0-derived.json` (raw-memory layer) now stores encrypted raw quantities plus a consistent `SaveBlock2` pointer/key; `emerald-us-rev0.source.json` (acquisition/source layer) correctly retains decoded `8`/`3`/`1` and was unmodified, since it was already defined to hold decoded values.
- Confirmed no schema, mapping, event/rule/action, notification, or proof-session/orchestrator files were touched, and the `<= 999` quantity bound in `emerald-us-rev0-source.schema.json` is unchanged.
- Ran the full `npm test` (370 passed, 1 pre-existing skip, 0 failed) plus targeted syntax/JSON/`git diff --check`/binary/status audits; all clean.

Non-blocking observations (do not block merge):
- `test/emerald-provider-parity.test.js` establishes JS/BizHawk-label parity by invoking the same JS `readEmeraldAcquisition` under two source labels, not by executing the Lua file itself; genuine Lua-path assurance here is manual source-level comparison (performed during this review) plus the existing address-pinning test, consistent with this repo's established, previously-reviewed limitation that CI cannot execute BizHawk's/mGBA's embedded Lua runtime.
- No automated test cross-checks the Lua `SAVEBLOCK2.encryptionKeyOffset` constant against the JS `saveBlock2.encryptionKeyOffset` constant directly (only address constants are cross-checked via regex); this review manually confirmed both are `0xAC`.
