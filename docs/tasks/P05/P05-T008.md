## Objective

Add a small, developer-only, read-only local tool for inspecting live Emerald memory/state while BizHawk or mGBA is running, to accelerate identifying and verifying new acquisition fields for the upcoming live-dashboard enrichment task, without becoming a full Workbench or a production feature.

## Scope

- A new, separate Lua diagnostic connector per provider (`adapters/bizhawk/memory-explorer-connector.lua`, `adapters/gen3-mgba/memory-explorer-connector.lua`) that reads a checked-in-format watch list and an optional bounded byte-range scan, and republishes raw values to a local diagnostic file. No decoding, no game semantics, no strict identity gating (this is diagnostic, not the production acquisition path).
- A pure, dependency-free JS logic module (`tools/emerald-memory-explorer-lib.mjs`) for hex formatting, signed-value derivation, and current-vs-previous change classification.
- A read-only local HTTP server (`tools/emerald-memory-explorer-server.mjs`) exposing exactly three GET endpoints (raw watches, provider-neutral Emerald source snapshot, normalized Pokemon state) plus the static developer UI. No POST/PUT/DELETE route exists anywhere in the server.
- A launcher (`tools/launch-emerald-memory-explorer.mjs`) that generates the watch list from `EMERALD_US_REV0.addresses` (one source of truth, not hand-duplicated) and launches BizHawk/mGBA with the diagnostic connector instead of the production one, reusing the existing per-provider local config loaders purely for already-validated executable/ROM/savestate paths.
- A static developer UI (`public/emerald-memory-explorer/`) with three architecturally separate panels: raw watched memory (hex/typed/diffed), the provider-neutral Emerald source snapshot, and the normalized Pokemon overlay state - so raw bytes, acquisition-layer semantics, and domain-normalized semantics are never conflated on screen.
- `npm run explore:emerald` (server) and `npm run explore:launch -- --provider bizhawk|mgba` (launcher) scripts.

## Non-Goals

- Not a full Workbench, not an unknown-value Cheat-Engine-style scanner (only a small, explicitly bounded - max 4096 bytes - opt-in range scan is included).
- No writes to emulator memory anywhere in this tool - the connectors are read-only, and the local server has no mutation endpoint at all.
- No changes to the production acquisition/mapping/domain/overlay path, and no game semantics added to either emulator provider.
- Does not itself implement the live-dashboard enrichment (nickname/species/moves/etc.) - that is the next task, informed by this tool's availability but not blocked on using it live (no ROM/emulator is available in this implementation environment; see Result).

## Implementation Notes

**Where the watch definitions live:** rather than hand-maintaining a second address list (drift risk against `EMERALD_US_REV0.addresses`, the already-reviewed single source of truth), the launcher imports that JS object directly and generates a `.lua`-loadable watch-list file at launch time, loaded via `loadfile()` - the same pattern the production connectors already use for the shared acquisition module. No JSON parser had to be written in Lua.

**Typed interpretation strategy:** the Lua connectors read u8/u16/u32 raw values per watch (using each provider's already-verified read functions - `memory.read_u8/u16_le/u32_le(address, "System Bus")` for BizHawk, `emu:read8/16/read32` for mGBA) and emit only those three raw numbers. Signed (s8/s16/s32) interpretation is derived client-side from the raw unsigned values in `emerald-memory-explorer-lib.mjs`, keeping the Lua side minimal and avoiding any bitwise-arithmetic risk in Lua.

**Why a separate connector, not a mode flag on the production one:** the production connectors (`proof-connector.lua`, `emerald-acquisition.lua`) perform strict identity/domain-parity gating and emit the acquisition source contract - mixing an open-ended raw-watch diagnostic into that path would either weaken its fail-closed guarantees or bloat it. A parallel, explicitly-diagnostic connector keeps both simple and keeps "Do not add game semantics to the BizHawk provider itself" true for both.

**mGBA's frame-count API was not verified in this session** (no confirmed record of a `emu:currentFrame()`-equivalent function from prior research in this environment), so the mGBA diagnostic simply omits a frame counter rather than guess at an unverified API call that could throw. BizHawk's diagnostic does include `emu.framecount()`, which was already verified in `P05-T006`/`P06-T001`'s review.

**No live verification was possible in this environment**: no BizHawk/mGBA installation and no legally obtained Emerald ROM are available here, consistent with every prior task in this project. The connectors' Lua syntax was hand-reviewed carefully (balanced braces/quotes, reuse of already-verified read/write patterns from the production connectors) but not executed against a real emulator. The Node-side server/launcher/lib were fully exercised for real: a real HTTP server was started and hit with real requests, and the launcher's `--check` path was run against real disposable stand-in files, generating a real, inspected `.lua` watch file.

## Security/Compatibility Considerations

Read-only by construction: the local server has no route that accepts a body or performs a write, and both Lua connectors only call read functions against emulator memory (verified by direct code reading - no `memory.write_*`/`emu:write*` call appears anywhere in either connector). Candidate watch labels typed into the UI are stored in the browser's `localStorage` only and are never sent to the server or written to any repository file. No ROM, save, savestate, or emulator binary is committed. This is explicitly developer-only tooling, not exposed to or intended for end users of the overlay.
