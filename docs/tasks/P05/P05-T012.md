## Objective

Replace manually coordinating three separate terminals (`npm run proof:bizhawk`, `npm run live:emerald`, `npm start`) for a BizHawk Emerald proof session with a single operator command, `npm run proof:emerald:bizhawk`, that owns the whole session's lifecycle - launch, readiness, log output, and clean shutdown - while reusing every existing, already-reviewed piece unmodified.

## Scope

- `tools/proof-session.mjs` (new) - a reusable, emulator-agnostic child-process lifecycle primitive: ordered spawn gated on per-child readiness signals, `[label]`-prefixed log streaming, real TCP port-availability checking, and coordinated termination (manual, on startup failure, or on an unexpected critical-child exit) via tracked-PID `kill()` calls only.
- `tools/proof-emerald-bizhawk.mjs` (new) - the small BizHawk-specific composition on top of the primitive, run via the new `npm run proof:emerald:bizhawk` script.
- `package.json` - adds the `proof:emerald:bizhawk` script; no existing script changed.
- `docs/decisions/0023-proof-session-orchestrator.md` (new ADR).
- Documentation pointers to the new one-command workflow in `adapters/bizhawk/README.md`, root `README.md`, and `docs/project/configuration.md`, alongside the still-available individual commands.

## Non-Goals

- No changes to `bizhawk-proof-config.mjs`, `emerald-live-state.mjs`, or `dev-server.mjs` - all three are reused exactly as they already exist and are already reviewed.
- No renaming of the existing `npm run proof:emerald` (mGBA) script to fit a future `proof:emerald:mgba` naming scheme - a compelling reason to touch an existing command name was not present in this task; harmonizing it is a named follow-up.
- No `proof:emerald:mgba` or `proof:emerald:libretro` implementation. `tools/proof-session.mjs` is built as the shared machinery those will eventually reuse, but building either provider-specific composition is explicitly out of scope here.
- No changes to, or dependency on, the unmerged `P05-T007` Libretro spike branch.
- No automatic port selection when the configured port is occupied - see Implementation Notes for the chosen fail-closed policy.
- No production video/audio/input handling, no changes to what the real-ROM BizHawk acceptance session (the actual `P05`/`P06` gate) requires or observes.

## Acceptance Criteria

- `npm run proof:emerald:bizhawk -- --check` validates BizHawk config, ROM/executable/connector file existence, and port availability, and spawns zero processes regardless of outcome.
- `npm run proof:emerald:bizhawk` launches BizHawk (with the connector and optional savestate, via the existing reviewed launch-descriptor logic), then the mapper, then the server, each gated on the previous one's own readiness signal, and prints the real overlay URL once the server is actually listening.
- Child process output is prefixed and interleaved clearly (`[bizhawk]`/`[mapper]`/`[server]`); BizHawk's own lack of meaningful stdout is disclosed, not hidden behind a fabricated signal.
- The configured port being occupied fails the session closed, before any process is spawned, with a clear message - no silent alternate-port selection.
- Any child failing to start, or a child exiting unexpectedly after the session is up, terminates the rest of the session's tracked children - no orphaned processes.
- Ctrl+C terminates every process the session itself spawned.
- Termination never touches a process the session did not spawn, regardless of executable-name similarity.
- All of the above works correctly on Windows, accounting for the fact that a non-detached Node child process is not automatically terminated when its parent exits.
- Existing individual commands (`npm run proof:bizhawk`, `npm run live:emerald`, `npm start`) remain unchanged and functional.

## Implementation Notes

**Two-layer split.** `tools/proof-session.mjs` contains zero Pokemon/Emerald/BizHawk/mGBA-specific code - it operates purely on caller-supplied child specifications (`command`/`args`/`env`/`ready`/`captureOutput`/`critical`). `tools/proof-emerald-bizhawk.mjs` is the only file that knows BizHawk exists; it builds the three child specs from an already-validated `bizhawk-proof-config.mjs` config object and hands them to the primitive. This mirrors the existing Provider/Game-adapter split already established elsewhere in this repository (`docs/knowledge/adapter-contracts.md`), applied to process orchestration instead of memory acquisition.

**Reused, not duplicated.** `buildSessionChildren()` calls the existing `createBizHawkLaunch(config)` once and reuses its `executable`/`args`/`environment` verbatim for the `bizhawk` child, and reuses that same `environment` object (already containing `EMERALD_SOURCE_SNAPSHOT_PATH`, `EOE_LIVE_STATE_PATH`, `EMERALD_MAPPING_POLL_INTERVAL_MS`, `PORT`) for the mapper and server children too - propagation is "reuse the same object," not "re-derive the same values a second time." A dedicated test (`buildSessionChildren reuses createBizHawkLaunch's own executable/args/environment verbatim`) pins this down directly rather than only checking the resulting values happen to match.

**Readiness signals are real evidence, not inferred.** The mapper and server children are gated on real, pre-existing log lines those scripts already print at genuinely meaningful moments (`emerald-live-state.mjs`'s `"Watching Emerald source snapshot:"`, printed only after its own config validation succeeds; `dev-server.mjs`'s `"running at http://"`, printed only inside its `listen()` success callback, i.e. only once the port is actually bound). BizHawk has no such signal available - it is a GUI application whose Lua console writes to its own panel, not this process's stdout - so its readiness is `"spawn"` (the OS confirmed the process started), and this is disclosed explicitly in code comments, the printed session banner, and this record: it is not a claim that the connector has loaded or a ROM is playable.

**Port-conflict policy: fail closed.** Considered auto-selecting a different port when the configured one is occupied; rejected it because a URL printed for a port the operator did not configure is a real, avoidable source of confusion, and `PORT` is already a one-line change in `.env.bizhawk.local`. `checkPortAvailable()` binds a real throwaway socket and closes it - not a fixed-list guess - so this check reflects actual OS socket state at call time.

**Windows process-lifecycle correction (caught during manual real-CLI testing, not assumed).** The first draft of `tools/proof-emerald-bizhawk.mjs`'s "is this the main module" guard compared `import.meta.url` against `` `file://${process.argv[1]}` `` (string concatenation). This is silently wrong on Windows: `process.argv[1]` is a Windows-style path (backslashes, no URL scheme, no extra leading slash before the drive letter), which never textually matches `import.meta.url`'s real `file:///C:/...` form - the guard's condition was always false, so the CLI entry point never ran at all when invoked directly (`node tools/proof-emerald-bizhawk.mjs`), with **no error and exit code 0**, the worst kind of silent failure. Caught by manually running the real command against a real (fake-content) local config rather than trusting the exported-function tests alone, which never exercise this file's own bottom-of-file entry point. Fixed using `pathToFileURL(process.argv[1]).href` (Node's own documented, platform-correct way to perform this comparison) instead of manual string concatenation.

**Termination is PID-based only.** `runProofSession`'s `terminate()` calls `.kill()` on each tracked `ChildProcess` object, never an image-name-based kill (e.g. `taskkill /IM`) - a dedicated test spawns a decoy "unrelated" fake process sharing a tracked child's command name but never registered with the session, and asserts the session's cleanup never touches it.

**Windows non-detached-child note.** `ChildProcess#kill()` maps to `TerminateProcess()` on Windows, which is already immediate/forceful - there is no real SIGTERM-then-SIGKILL escalation to implement, and (unlike POSIX) nothing about spawning non-detached automatically ties a child's lifetime to the parent's, so every child is explicitly tracked and explicitly killed during shutdown rather than relying on implicit OS cleanup.

**No real BizHawk available.** Consistent with every other `P05`/`P06` task in this phase: no legally obtainable Emerald ROM or licensed BizHawk build is available in this environment. The `bizhawk` child slot's real spawn-success and spawn-failure paths were verified against a real (non-executable placeholder) file via the actual CLI, proving the orchestrator's error handling and cleanup work correctly end-to-end for a real OS-level spawn failure (`spawn UNKNOWN`, correctly reported and cleaned up, exit code 1). The mapper/server readiness-and-cleanup machinery was separately verified against two genuinely real, long-running Node child processes. What was **not** verified here - and cannot be, without an operator-supplied real BizHawk/ROM - is the full three-real-process happy path with a real BizHawk in the `bizhawk` slot; that remains part of the same real-ROM acceptance session every prior `P05`/`P06` task has already carried at this stage, not a new gap this task introduces.

## Security/Compatibility Considerations

No ROM, BIOS, save, savestate, or emulator binary is committed or required to exist for the automated test suite (fixture files used in tests are empty placeholders whose existence, not content, is checked). No new runtime dependency was added. `.env.bizhawk.local` continues to be the only source of real local paths and remains gitignored; nothing new is written outside the paths that configuration already specifies. Process termination is strictly PID-based (never executable-name-based), specifically to avoid the real risk of a session accidentally terminating an unrelated process that happens to share an executable name (e.g. another BizHawk instance the operator has open for an unrelated purpose).

- **Startup ordering (bizhawk → mapper → server) and readiness gating:** ran the real `tools/proof-session.mjs` primitive with three genuine child processes - a Node stand-in for the `bizhawk` slot (no real BizHawk executable is obtainable in this environment, the same disclosed, environment-wide limitation as every other `P05`/`P06` task) and the actual, unmodified `tools/emerald-live-state.mjs` and `tools/dev-server.mjs` scripts for the other two.
