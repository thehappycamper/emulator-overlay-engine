## Objective

Add two related, provider-neutral Pokemon runtime capabilities: (A) a semantic `player.party.defeated` event firing on the transition from "at least one usable party member" to "zero usable party members," wired through the existing P04 rule/action/executor path to an `overlay.notification`; and (B) live battle stat-stage (Attack/Defense/Speed/Sp. Atk/Sp. Def/Accuracy/Evasion, `-6..+6`) acquisition and presentation for the player's and opponent's single active battlers in Emerald.

## Why This Task Exists

(A) The engine currently has no event for a full party wipe, even though `pokemon.fainted` already exists per-individual. (B) `docs/tasks/P05/P05-T010.md` investigated battle stat stages and explicitly left them unresolved: it could not find or independently verify a trustworthy fixed EWRAM address for `gBattleMons` in this environment (no compiler/emulator available to produce a real symbol map) and disclosed this as a known gap. This task closes that gap by finding an independently cross-checkable community linker/RAM map for the exact same retail build already used elsewhere in this codebase.

## Implementation Notes

**Part A - `player.party.defeated`.** `partyHasAnyUsableMember(party)` returns `true`/`false`/`null` (not enough information) so the detector (`previousUsable !== true || currentUsable !== false` -> no event) can never fabricate a defeat from missing HP data or an empty party. It deliberately does not use `matchPartyMembers`/identity matching at all - only the aggregate "is anyone still standing" between two snapshots - so a pure reorder can never trip it. This was verified against every example transition in the task brief, including revive-then-second-defeat (fires twice) and repeated all-fainted snapshots (fires once). One pre-existing test ("a battling Pokemon fainting..." in `pokemon-events.test.js`) legitimately gained the new event type in its expected set, since its one-Pokemon-party scenario is a genuine party defeat, not a false positive.

**Part B - `gBattleMons` address.** `pokeemerald`'s own decompiled source (confirmed via a live fetch of `include/pokemon.h`, `include/constants/pokemon.h`, `include/constants/battle.h`) has no fixed numeric address for `gBattleMons` - only `extern struct BattlePokemon gBattleMons[MAX_BATTLERS_COUNT]`. `MAX_BATTLERS_COUNT` is `4`; battler `0` is the player's single active battler and battler `1` is the opponent's, per `enum BattlerId`/`enum BattlerPosition` ordering, for the single (non-double) battle format this adapter already exclusively supports. `struct BattlePokemon` (`include/pokemon.h`) places `s8 statStages[NUM_BATTLE_STATS]` at offset `0x18`; `NUM_BATTLE_STATS` is `8` (`include/constants/pokemon.h`: `NUM_STATS` (6) + Accuracy + Evasion), index `0` (`STAT_HP`) unused, indices `1..7` = Atk/Def/Speed/SpAtk/SpDef/Acc/Evasion in that order. `MIN_STAT_STAGE`/`DEFAULT_STAT_STAGE`/`MAX_STAT_STAGE` are `0`/`6`/`12` (same header), confirmed against `src/battle_util.c`'s own `< DEFAULT_STAT_STAGE` comparisons; the struct's own `sizeof` is `0x58` (last field `otId` at `0x54`, a `u32`).

The address itself was found in `Bird404/Pokemon-Emerald-Battle-Engine-Upgrade`'s `BPEE.ld` (a community-maintained linker/RAM map for this exact retail build, also independently mirrored verbatim in `Gamer2020/Shiny_Hack`'s copy): `battle_participants = 0x02024084` (its name for `gBattleMons`). The same file independently states `sav1 = 0x03005D8C`, `sav2 = 0x03005D90`, `party_player = 0x020244EC`, `party_opponent = 0x02024744`, and `battle_flags = 0x02022FEC` - all five of which exactly match this codebase's own, separately-established addresses. That 5-for-5 cross-check is the corroboration for treating `battle_participants` as trustworthy too, following the same "community RAM-map research" precedent `P05-T015` already used and this project already accepted for `saveBlock2Pointer`. This is the same category of evidence P05-T010 was missing, not a compiled symbol map (no C toolchain is available in this environment - confirmed unchanged).

Both battlers' stat-stage reads are wrapped together: if either raw byte falls outside `[0,12]`, *both* battlers' stages become `null` (not a partial result), matching the project's established fail-closed convention. `gBattleMons` is a fixed global (unlike `SaveBlock1`/`SaveBlock2`'s pointer indirection) so it is always numerically "readable" even outside battle; range validation is the only fail-closed signal, which is why reads are additionally gated on `battleActive`.

## Review Findings

Independent review (fresh, from `65d825b`/`1b21445`, not trusting the implementation's own report): **APPROVE**, after two small fix commits applied during review.

**Part A verification.** Wrote an independent probe script (not the implementation's own test file) exercising 17 scenarios: one-member 1->0, `[0,12]->[0,0]`, repeated all-zero (no duplicate), empty party (both sides), missing/unknown HP (both sides, and mixed known/unknown), reorder while alive, reorder while all-fainted, revive after defeat, second defeat after revival, and two membership-change-during-transition cases (member added while another already fainted; the only usable member removed). All 17 matched expected semantics exactly. Confirmed directly from source that `detectPartyDefeated`/`partyHasAnyUsableMember` never call `matchPartyMembers`/`pokemonIdentityKey`/`collectTrackedPokemonPairs` - the aggregate check is genuinely identity-independent, so it cannot inherit P03's ambiguous-identity problem. Traced `tools/emerald-live-state.mjs`'s `processEmeraldEvents` to confirm the real path is `detectPokemonEvents -> evaluateRules -> executor.executeAll` (the real capability-gated executor via `createActionExecutor`), with no direct event-to-presentation shortcut.

**Part B upstream verification (independent, not reusing the implementation's citations).** Fetched `pret/pokeemerald`'s `include/pokemon.h`, `include/constants/pokemon.h`, `include/constants/battle.h`, and `src/pokemon.c` live. Confirmed `struct BattlePokemon.statStages` at offset `0x18`, struct size `0x58`, `NUM_BATTLE_STATS = 8` (`STAT_HP=0` unused, `STAT_ATK=1..STAT_EVASION=7`), and `MIN/DEFAULT/MAX_STAT_STAGE = 0/6/12`. Found stronger evidence than the implementation cited for the `-6..+6` transformation: `src/pokemon.c`'s `gStatStageRatios` table carries the game's own source comments `{10,40}, // -6, MIN_STAT_STAGE` through `{40,10}, // +6, MAX_STAT_STAGE`, an explicit authoritative statement of the encoding (not just inferred from comparison operators).

**Address verification (treated as high-risk per review instructions).** Independently confirmed the implementation's own citation: `Bird404/Pokemon-Emerald-Battle-Engine-Upgrade`'s `BPEE.ld` states `battle_participants = 0x02024084` alongside five other addresses that all exactly match this codebase's already-verified constants; confirmed this is a real, functioning ASM-patch framework (20 forks, uses devkitARM to actually compile and patch a working ROM - address errors there would produce a broken game, not merely a wrong wiki entry). Then went further than the implementation report and found a **second, fully independent** source: Glitch City Laboratories (a highly-regarded Gen III RE/glitch-research community, unconnected to any ROM-hacking-patch lineage) - a 2014 forum post by "Torchickens" states "*to track or modify the first move of your Pokémon currently in battle, change 16-bit address... 02024090*." `0x02024090 = 0x02024084 (claimed `gBattleMons` base) + 0x0C` (`moves[]`'s offset in `struct BattlePokemon`) - i.e. `gBattleMons[0].moves[0]` exactly, and "your Pokémon" independently confirms battler `0` = player. The same community independently stated `0x020244EC` is "the party," matching this codebase's `playerParty` constant. This is genuine multi-source, differently-sourced corroboration (source #3 on the review's own preference order), not a single lineage repeated. No C toolchain is available in this environment to reproduce the address by compiling (same constraint `P05-T010` disclosed); this was not attempted.

**Fail-closed adversarial probing (independent script, not the committed tests).** Verified: baseline decode produces the fixture's real distinct player/opponent stages; a raw byte of `13` or `255` on either battler nulls **both** battlers (not just the offending one); a reader that throws on a stat-stage byte is caught and nulls both; not-in-battle produces `battle.opponent === null` and `battle.player.statStages === null` (never `0`); raw `0` and `12` are correctly accepted as valid (`-6`/`+6`), not rejected as boundary errors.

**JS/Lua parity.** Read both implementations line by line (not just running the automated constant cross-check): identical `BATTLE` constants, identical `STAT_STAGE_FIELD_ORDER`, identical `battlerAddress = base + index*stride` arithmetic, identical `+1..+7` byte-offset iteration (Lua's 1-based loop naturally produces the same byte range as JS's `+1+index`), identical "both battlers null together" fail-closed semantics (JS via try/catch around both calls, Lua via an explicit `~= nil` check on both results before assigning - different mechanisms, verified equivalent observable behavior). Confirmed the automated cross-check test actually runs and passes, and separately confirmed by mutation (reversing `playerBattlerIndex`/`opponentBattlerIndex`) that 4 tests - including that cross-check - catch a player/opponent swap. Genuine Lua execution remains untested (no interpreter available); this is disclosed, not hidden.

**Blocking-adjacent findings, fixed during this review (commit `5469639`):**
1. **Accuracy/Evasion were never rendered anywhere.** The data layer correctly acquired `statStages.acc`/`statStages.eva` in both JS and Lua, but `presentation.js` never displayed them (`STAT_COMPARISON_ROWS` only covered Attack/Defense/Sp.Atk/Sp.Def/Speed) - despite the task's own requirement that "Accuracy/evasion should be represented too if authoritative data is acquired." It was acquired, so this was a real gap, not a disclosed scope cut. Fixed: added `STAT_STAGE_ONLY_ROWS` (two new table rows showing only the stage badge, no numeric comparison, since accuracy/evasion have no underlying base stat to compare) plus a regression test.
2. **No regression test for "unknown HP is not fainted."** The detector's own code correctly treats missing/unreadable `currentHp` as "not enough information" (verified independently, see above), but no committed test locked this in - confirmed by mutation: a version of `partyHasAnyUsableMember` that treats missing HP as `0` passed the entire existing `pokemon-events.test.js` suite unmodified. Fixed: added a dedicated test (also covering a mixed known/unknown-HP party), then re-confirmed it now fails against the same mutation before reverting the mutation.
3. **Overclaiming doubles scope.** A source comment said battler 0/1 were used "for the only battle format this adapter already exclusively supports," but there is no runtime `BATTLE_TYPE_DOUBLE` check anywhere in the adapter (confirmed by grep) - during an actual double battle, stat stages would still read battler 0/1 and present them without any indication a second battler pair exists. This mirrors a pre-existing, already-accepted limitation in the rest of this adapter (the opponent/catch-odds reading has never gated on doubles either), so it is **not new risk** and does not block, but the wording overclaimed enforcement that doesn't exist. Fixed: reworded the comment to state plainly that this is an undetected scope decision, not a runtime gate.

**Non-blocking observations (no fix required):** double-battle behavior, opponent-replacement mid-trainer-battle, and player-switch scenarios could not be exercised against real runtime state (no live emulator in this environment); by construction (fresh reads every acquisition call, no memoization) these should behave correctly, but this is inference, not observed behavior. Real BizHawk/Emerald acceptance was not performed - stated explicitly, not implied.

**Scope audit:** confirmed clean - no BizHawk-specific stat-stage code (`grep` of `adapters/bizhawk/` for `battleMonsAddress`/`statStages`/`player.party.defeated` returns nothing), no `game.blackout` implementation (only a comment explaining why it's out of scope), `activePlayerIndex` untouched, no schema-bound relaxation (only additive `required`/property entries), no proof-session/orchestrator/notification-feed files touched, mapping diff is exactly two new field mappings plus a version bump.

**Validation:** full `npm test` after fixes: 390 passed, 1 pre-existing skip, 0 failed (2 net new tests from the fix commit). JS/Lua syntax (`node --check`, `luaparse` with `luaVersion: '5.3'`), JSON/schema validation, `git diff --check`, and a NUL/binary audit all clean.
