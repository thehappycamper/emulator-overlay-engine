## Objective

Add two related, provider-neutral Pokemon runtime capabilities: (A) a semantic `player.party.defeated` event firing on the transition from "at least one usable party member" to "zero usable party members," wired through the existing P04 rule/action/executor path to an `overlay.notification`; and (B) live battle stat-stage (Attack/Defense/Speed/Sp. Atk/Sp. Def/Accuracy/Evasion, `-6..+6`) acquisition and presentation for the player's and opponent's single active battlers in Emerald.

## Why This Task Exists

(A) The engine currently has no event for a full party wipe, even though `pokemon.fainted` already exists per-individual. (B) `docs/tasks/P05/P05-T010.md` investigated battle stat stages and explicitly left them unresolved: it could not find or independently verify a trustworthy fixed EWRAM address for `gBattleMons` in this environment (no compiler/emulator available to produce a real symbol map) and disclosed this as a known gap. This task closes that gap by finding an independently cross-checkable community linker/RAM map for the exact same retail build already used elsewhere in this codebase.

## Implementation Notes

**Part A - `player.party.defeated`.** `partyHasAnyUsableMember(party)` returns `true`/`false`/`null` (not enough information) so the detector (`previousUsable !== true || currentUsable !== false` -> no event) can never fabricate a defeat from missing HP data or an empty party. It deliberately does not use `matchPartyMembers`/identity matching at all - only the aggregate "is anyone still standing" between two snapshots - so a pure reorder can never trip it. This was verified against every example transition in the task brief, including revive-then-second-defeat (fires twice) and repeated all-fainted snapshots (fires once). One pre-existing test ("a battling Pokemon fainting..." in `pokemon-events.test.js`) legitimately gained the new event type in its expected set, since its one-Pokemon-party scenario is a genuine party defeat, not a false positive.

**Part B - `gBattleMons` address.** `pokeemerald`'s own decompiled source (confirmed via a live fetch of `include/pokemon.h`, `include/constants/pokemon.h`, `include/constants/battle.h`) has no fixed numeric address for `gBattleMons` - only `extern struct BattlePokemon gBattleMons[MAX_BATTLERS_COUNT]`. `MAX_BATTLERS_COUNT` is `4`; battler `0` is the player's single active battler and battler `1` is the opponent's, per `enum BattlerId`/`enum BattlerPosition` ordering, for the single (non-double) battle format this adapter already exclusively supports. `struct BattlePokemon` (`include/pokemon.h`) places `s8 statStages[NUM_BATTLE_STATS]` at offset `0x18`; `NUM_BATTLE_STATS` is `8` (`include/constants/pokemon.h`: `NUM_STATS` (6) + Accuracy + Evasion), index `0` (`STAT_HP`) unused, indices `1..7` = Atk/Def/Speed/SpAtk/SpDef/Acc/Evasion in that order. `MIN_STAT_STAGE`/`DEFAULT_STAT_STAGE`/`MAX_STAT_STAGE` are `0`/`6`/`12` (same header), confirmed against `src/battle_util.c`'s own `< DEFAULT_STAT_STAGE` comparisons; the struct's own `sizeof` is `0x58` (last field `otId` at `0x54`, a `u32`).

The address itself was found in `Bird404/Pokemon-Emerald-Battle-Engine-Upgrade`'s `BPEE.ld` (a community-maintained linker/RAM map for this exact retail build, also independently mirrored verbatim in `Gamer2020/Shiny_Hack`'s copy): `battle_participants = 0x02024084` (its name for `gBattleMons`). The same file independently states `sav1 = 0x03005D8C`, `sav2 = 0x03005D90`, `party_player = 0x020244EC`, `party_opponent = 0x02024744`, and `battle_flags = 0x02022FEC` - all five of which exactly match this codebase's own, separately-established addresses. That 5-for-5 cross-check is the corroboration for treating `battle_participants` as trustworthy too, following the same "community RAM-map research" precedent `P05-T015` already used and this project already accepted for `saveBlock2Pointer`. This is the same category of evidence P05-T010 was missing, not a compiled symbol map (no C toolchain is available in this environment - confirmed unchanged).

Both battlers' stat-stage reads are wrapped together: if either raw byte falls outside `[0,12]`, *both* battlers' stages become `null` (not a partial result), matching the project's established fail-closed convention. `gBattleMons` is a fixed global (unlike `SaveBlock1`/`SaveBlock2`'s pointer indirection) so it is always numerically "readable" even outside battle; range validation is the only fail-closed signal, which is why reads are additionally gated on `battleActive`.
