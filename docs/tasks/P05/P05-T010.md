## Objective

Add an expandable battle stat comparison to the Pokemon overlay so the player can compare their active Pokemon's stats against the current opponent's without permanently consuming dashboard space, reusing `P05-T009`'s already-decoded per-Pokemon fields rather than duplicating any acquisition work.

## Scope

- A collapsed-by-default, expandable "Compare Stats" panel inside the existing battle section, rendered only while a battle is active.
- Side-by-side comparison of Attack, Defense, Sp. Atk, Sp. Def, Speed, current/max HP, and Level, with a relative indicator (`>`, `<`, `=`) per row, styled to make the advantaged side visually clear.
- Genuinely missing/unusable stat values render as an explicit "unavailable" marker (`&ndash;`) with no indicator, never a fabricated number.
- Reuses `player.party` and `battle.opponent`/`battle.activePlayerIndex` - fields `P05-T009` and earlier tasks already decode and validate. No new acquisition, mapping, or schema change of any kind.

## Why No New Acquisition/Schema Work Was Needed

Every field this panel needs - `stats.{atk,def,spa,spd,spe}`, `currentHp`, `maxHp`, `level` for both `player.party[n]` and `battle.opponent` - was already decoded, mapped, and schema-validated by `P05-T009` (merged to `main`). `battle.activePlayerIndex` already exists in the target schema and sample state too, so no extension was required there either. This task is presentation-only.

## Investigation: Battle Stat Stages And Active-Battler Tracking

Per the task request, investigated whether Emerald's live battle memory already exposes the two additional things a fuller comparison would want:

1. **Battle stat stages** (`+1`/`-2` modifiers for Attack/Defense/Sp. Atk/Sp. Def/Speed/Accuracy/Evasion). In `pokeemerald`, these live in the runtime battle-engine struct `gBattleMons[battlerId].statStages[]` (`include/battle.h`'s `struct BattlePokemon`), not in the save block. Unlike every address this project has used so far (`playerParty`, `enemyParty`, `battleTypeFlags`, `mainInBattleFlags`, `saveBlock1Pointer` - all already in `EMERALD_US_REV0.addresses`), `pokeemerald`'s own source does not contain a fixed numeric address for this struct; the decompilation only has the symbolic name, and the real address is whatever the linker assigns to a specific compiled build (US, Rev 0). Existing addresses in this codebase were established before this task and have no documented source trail I can verify or extend; this environment has no live emulator/debugger and cannot compile `pokeemerald` to produce a fresh symbol/map file to confirm a new address for `gBattleMons`. I could not find or independently verify a citable, trustworthy address for this build.
2. **Which party slot is the active battler.** The equivalent problem: this is tracked by a runtime battle-engine array (`gBattlerPartyIndexes` or equivalent), not the save block, and has the same "no verifiable fixed address in this environment" limitation.

Per the task's own explicit instruction ("If it requires substantial new battle-structure work, document it as the immediate follow-up and do not guess or fabricate values"), **both are deferred rather than guessed at.** `battle.activePlayerIndex` remains the pre-existing placeholder it already was (always `0`, from a literal mapping default `P05-T004` introduced), and this task's panel explicitly discloses that in its own UI text ("active-battler tracking is not yet implemented") rather than presenting party slot 1 as a verified "your active Pokemon." No stat-stage modifiers are rendered, since none are decoded.

## Information-Policy Note

This panel shows values the acquisition layer can already read from the opponent's decoded Pokemon record (species, level, stats, current HP, status, types) exactly as the rest of the dashboard already does - it does not read or expose anything new that wasn't already technically observable and already shown elsewhere in the existing opponent card. No new hidden-information boundary is crossed. That said, per the request: **technically observable in emulator memory is not the same as intentionally exposed to presentation.** This project has no permissions/ruleset system today, and none is added here. A future ruleset or template (e.g. a "blind battle" or nuzlocke-style challenge mode) may legitimately want to hide some of what this panel or the opponent card already shows (for example, exact stats or HP) even though the emulator can technically read it. That is a real, disclosed future need, not solved by this task - see Follow-Up Tasks.
