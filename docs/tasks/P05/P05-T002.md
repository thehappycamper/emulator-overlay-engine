## Objective

Prove that repository-owned code running through mGBA's supported Lua interface can identify an exact Pokemon Emerald revision and read a small set of changing live gameplay values. This task ends at a developer diagnostic and does not define the source contract or normalized output.

## Why This Task Exists

`P02` completed the Pokemon domain boundary, while `P05` still had only adapter notes. Before designing source/mapping/transport contracts around assumptions, the project needs one real acquisition proof against the emulator and retail memory layout.

## Scope

- Strictly identify English retail Pokemon Emerald Rev 0.
- Add a read-only mGBA 0.10.3 Lua diagnostic provider.

## Implementation Notes

Supported baseline:

- mGBA 0.10.3 desktop Lua scripting.
- English retail Pokemon Emerald Rev 0.
- Game code `AGB-BPEE`, internal title `POKEMON EMER`, header revision `0`.
- CRC32 `1F1C08FB`; pret reference SHA-1 `f3ae088181bf583e55daf962a92bb46f4f1d07b7`.

The Lua provider uses mGBA's `CoreAdapter` reads, ROM memory domain, CRC32 checksum, frame callback, and text buffer. It never invokes memory writes. The diagnostic is JSON-shaped for developer inspection but is explicitly not the future source or normalized-state contract.

`emerald-us-rev0.js` captures pure identity enforcement, the Gen III personality/OT-ID XOR species decryption, all 24 growth-substructure positions, direct level/HP offsets, battle flag interpretation, and SaveBlock pointer validation. The Lua provider mirrors this small layout because mGBA executes Lua directly; a synchronization test pins the address/CRC constants across both files.

Sources are official mGBA scripting documentation and the pret/pokeemerald source/decompilation. No unreviewed local script code was copied.

## Security/Compatibility Considerations

The provider is read-only and fingerprint-gated. Version-specific addresses remain under `adapters/`; no platform or domain module depends on them. SaveBlock pointers are range-checked before dereference, impossible party counts fail closed, and fixtures contain synthetic numbers only. The script should remain repository-reviewed executable code; this task does not establish safe dynamic extension installation.

## Review Findings

Independently reviewed against approved `main` (base/merge-base `cf13946`, branch HEAD `3bdfd49`). Verdict: **APPROVE**, no blocking findings. The review independently re-derived and verified, rather than merely reading, the core decoding logic: manually recomputed the 24-permutation Gen III growth-substructure position table from the known Bulbapedia/pret substructure ordering and it matched `GROWTH_SUBSTRUCT_INDEX` exactly; manually recomputed the species-decryption XOR and struct offsets against the fixture's raw memory values and reproduced both `expected.party.first` (speciesId 258) and `expected.battle.opponent` (speciesId 261) exactly; confirmed the 600-byte `playerParty`/`enemyParty` address delta is self-consistent with the correct 100-byte Gen III `PartyPokemon` struct size. Confirmed the fingerprint check fails safe (all gameplay reads gated behind a combined game-code/title/revision/CRC32 match, with an early return on mismatch). Confirmed `emerald-us-rev0.js` is a pure, dependency-injected module with zero emulator globals, mirroring the same architectural pattern independently used by the concurrent `P05-T001` branch. Confirmed no ROM/save/BIOS/binary material anywhere in the diff (binary-marker check, per-file size check, base64-blob grep all clean) and no new dependencies. Confirmed the diagnostic's JSON shape is structurally distinct from the Pokemon normalized-state schema, so this does not prematurely collapse into normalized state. Confirmed documentation honestly and repeatedly distinguishes the passing automated test suite from the still-unperformed manual live GUI smoke test. Independently re-ran `npm ci`/`npm test` (87/87 passing), `git diff --check` (clean), `node --check` on both new JS files (clean). One non-blocking note: the exact fingerprint constants (CRC32 value, exact `getGameCode()` return format) could not be independently certified without a running mGBA instance/ROM, which this review sandbox does not have — this is precisely what the still-pending manual smoke test will confirm, and the failure mode if any constant is imprecise is safe (the script reports `unsupported-rom` rather than misreading memory). No Lua interpreter was available in this sandbox to automatically check `.lua` syntax; it was read manually in full and found well-formed.
