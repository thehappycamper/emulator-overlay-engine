## Objective

Preserve live Emerald battle stages through the existing source-to-state path and show the Gen III stage-adjusted Attack, Defense, Sp. Atk, Sp. Def, and Speed values in Compare Stats without replacing raw stats.

## Why This Task Exists

The local live-state artifact for the reported Mudkip/Growl case already contains `battle.opponent.statStages.atk: -1`, while the comparison view treated the raw stat as its only numeric value. This task makes the existing stage data visible as a battle-relevant derived value and pins the full pipeline with regressions.

## Dependencies

`P05-T016` (merged battle stat-stage acquisition and presentation), the existing Emerald mapping, and the Pokemon normalized-state contract.

## Scope

- Add a Pokemon-domain Gen III stat-stage ratio/derivation utility.
- Add optional `stageAdjustedStats` to the Pokemon normalized-state schema and derive it after the existing declarative Emerald mapping.
- Render adjusted values as primary, retain raw values as `base` when non-neutral, and continue showing stage-only Accuracy/Evasion.
- Add acquisition-to-mapping-to-presentation and arithmetic regressions.
- Document the authoritative ratio source and the unchanged active-battler limitation.

## Non-Goals

No new memory acquisition, active-battler-slot tracking, doubles support, abilities/items/status modifiers, critical-hit rules, damage-engine redesign, or emulator writes.

## Acceptance Criteria

- Source `-1` reaches normalized `statStages` and the rendered comparison.
- Stage-adjusted values use the Gen III ratio table with positive integer truncation.
- Raw `stats` remain unchanged.
- Missing or out-of-range stages produce no derived value and do not fabricate neutral.
- Provider parity and existing overlay behavior remain intact.

## Implementation Notes

The current `public/live-state.json` was inspected before editing: Wurmple had raw Attack `7` and `statStages.atk: -1`. This establishes that the reported value was not lost in BizHawk acquisition, the source contract, or declarative mapping in that artifact; the presentation lacked a separate adjusted-stat representation. The new derivation is Pokemon-domain code after the generic mapping runtime, so shared mapping remains domain-neutral.

The ratio table is transcribed from [`pret/pokeemerald` `src/pokemon.c`](https://github.com/pret/pokeemerald/blob/master/src/pokemon.c#L1849-L1863): `gStatStageRatios` uses `{10,40}` through `{40,10}`, and its [`APPLY_STAT_MOD` macro](https://github.com/pret/pokeemerald/blob/master/src/pokemon.c#L3007-L3010) multiplies then divides using integer arithmetic. For positive stats this is truncation toward zero (`100` at `-1` is `66`; `7` at `-1` is `4`).

`stageAdjustedStats` is a stage-only view, not the complete effective battle stat. Ability, item, status, badge, and other modifiers remain outside this task. `activePlayerIndex` remains the existing slot-0 placeholder.

## Review Findings

Independent review (fresh, from `c7b77ae`/`2edbb71`, not trusting the implementation's own report): **APPROVE**, after one fix commit applied during review.

**Root cause tracing.** Independently confirmed the claimed pre-existing defect using a real local artifact: `public/live-state.json` (gitignored, never committed, predates this task) shows opponent WURMPLE with raw `stats.atk: 7` and `statStages.atk: -1` but no `stageAdjustedStats` key at all - exactly the reported shape. Traced the pipeline: acquisition/source-contract/declarative-mapping (all from `P05-T016`, unmodified here) correctly carry `statStages` through untouched; the actual boundary was that normalized state had no derived numeric consequence of the stage at all - presentation showed the raw stat and the stage badge side by side, never combined. This task's framing ("presentation lacked a separate adjusted-stat representation," not "the stage was lost") is accurate, not overclaiming a data-loss bug that didn't exist.

**Upstream math (independent re-fetch, not reusing prior citations).** Re-fetched `pret/pokeemerald`'s `src/pokemon.c` fresh and confirmed `gStatStageRatios[MAX_STAT_STAGE+1][2]` exactly matches the implementation's `GEN3_STAT_STAGE_RATIOS` table value-for-value (`{10,40}` at `-6` through `{40,10}` at `+6`), and `APPLY_STAT_MOD`'s exact form: `var = stat * ratio[0]; var /= ratio[1];` (multiply fully, then divide, C integer division truncating toward zero for these always-non-negative values) - matching `Math.trunc((base * numerator) / denominator)` precisely. Independently computed and verified via a fresh script (not the committed tests) every worked example in the review brief plus non-divisible cases: `100@+2=200`, `100@-1=66`, `7@-1=4` (the Wurmple case), `7@-2=3`, `7@0=7`, `7@+1=10`, `7@+2=14`, `7@+6=28`, `7@-6=1`, and a `5@-1=3` non-divisible case - all correct integer truncation, no floating-point rounding.

**Representation/architecture.** Confirmed via direct code reading that `stageAdjustedStats` is a new sibling field alongside untouched `stats`/`statStages` (never an overwrite) - independently probed with a mutation that overwrote `stats` with the adjusted view and confirmed 2 tests catch it. The derivation lives in a new Pokemon-domain module (`src/domains/pokemon/stat-stages.js`), consumed by the mapping layer (`emerald-state-mapping.js`) after the declarative mapping runs, matching the preferred `raw + stage -> domain derivation -> presentation-consumable value` architecture. Presentation also imports `calculateStageAdjustedStat` directly as a fallback; checked whether this is a "presentation-layer game math" violation and found it is not new/unjustified: `presentation.js` already imports and calls `projectIncomingDamage` from `damage.js` directly at render time (a pre-existing, foundational pattern from this project's original domain-boundary commit) - the fallback calls the same shared domain function rather than duplicating the ratio table, consistent with established convention.

**Real bug found and fixed (commit `c9ebbab`).** Testing the "prefer precomputed over recalculate" claim adversarially (supplying a deliberately-wrong `stageAdjustedStats` value and checking which number rendered) found the **opponent** column correctly preferred the precomputed value, but the **player** column always silently recalculated regardless of what was supplied - confirmed the number shown was still mathematically correct (the fallback recomputes identically), so this was not user-visible, but it meant `state.battle.player.stageAdjustedStats` (the schema-validated, mapping-layer-computed field the task added) was dead data for the real dashboard: nothing ever read it back out, so a future player-side-specific mapping bug would never surface on screen. Root cause: `presentation.js` read `activePlayer.stageAdjustedStats` (the party-slot Pokemon object), but the mapping layer attaches `stageAdjustedStats` only to `state.battle.player` (a separate object) - confirmed by reading `emerald-state-mapping.js` directly. Fixed by threading `state.battle.player.stageAdjustedStats` through as its own parameter, mirroring the existing `playerStatStages` threading; verified by reverting the fix and confirming a new regression test fails, then restoring.

**Pipeline/battle-exit (independent, real-fixture end-to-end trace, not just unit tests).** Mapped the real `emerald-us-rev0.source.json` fixture and independently recomputed both derived views by hand from its raw stats/stages, matching the committed test's exact expected values (player `{atk:13,def:36,spa:24,spd:8,spe:14}`, opponent `{atk:50,def:20,spa:10,spd:10,spe:20}`). Then constructed a battle-exit source (`active:false`, `opponent:null`, `player:{statStages:null}`) and confirmed through the real `mapEmeraldSourceSnapshot`+`renderPokemonOverlay` path that `battle.opponent` is entirely absent (not just its `stageAdjustedStats`), `battle.player` becomes `{statStages:null, stageAdjustedStats:null}` (no staleness), and the rendered HTML contains neither `stat-stage` nor `stat-compare` markup - the panel disappears cleanly, matching the existing pre-battle behavior established in `P05-T016`.

**Presentation.** Confirmed the Wurmple-equivalent case renders as `4 (-1) base 7` (adjusted value primary, stage badge, base shown only when non-neutral and different from the adjusted value) via a fresh probe, and via the committed `pokemon-stat-stages.test.js` end-to-end test. Confirmed `STAT_STAGE_ONLY_ROWS` (Accuracy/Evasion, from `P05-T016`) is untouched by this diff - still stage-badge-only, no numeric value - and independently confirmed by mutation (adding `acc`/`eva` to `BATTLE_STAT_KEYS`) that 3 tests would catch an accidental numeric Accuracy/Evasion stat.

**Semantic naming.** The schema's `stageAdjustedStats` description explicitly states "this is not the complete effective stat," satisfying the requirement that future ability/item/status/badge modifiers not be implied as already included.

**Regression-quality mutation testing (independent, reviewer-only, all reverted).** Beyond the player-wiring bug above: (1) `Math.trunc` -> `Math.round` caught by 4 tests; (2) `stats` overwritten by `stageAdjustedStats` caught by 2 tests; (3) `acc`/`eva` added to `BATTLE_STAT_KEYS` caught by 3 tests; (4) a statStages object present but missing exactly one key (all base stats present) was **not** caught by any test in the entire suite - a real, confirmed test-coverage gap (the existing "missing stages" test only covered a fully-null stage object and a missing base-stat case, never a partial-but-present stage object).
