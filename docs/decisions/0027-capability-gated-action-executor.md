# ADR 0027: Capability-Gated Action Executor

- **Status:** Accepted for the P04-T002 vertical slice
- **Date:** 2026-08-09

## Context

P04-T001 proved `semantic event -> declarative rule -> validated action request`, deliberately stopping at a descriptive, non-executable envelope: "no action executor, provider capability checks, emulator writes... or external integration." Its own recommended follow-up was to "define a capability-gated action-provider boundary and a minimal in-memory executor for approved local actions" while keeping "provider mutation and permissions outside rule evaluation."

The platform needs to prove that an action request can be turned into a real (but harmless) local effect without collapsing the separation between deciding what should happen (rules) and doing it (execution), and without assuming every future action is safe to run just because a rule asked for it.

## Decision

A new `src/actions/execute.js` module adds a fourth, wholly separate pipeline stage: `createActionExecutor(providers, options)` builds an executor bound at construction time to a fixed set of registered action providers and a fixed set of granted capability strings. `src/rules/evaluate.js` is not modified and does not import this module; the executor consumes the `ActionRequest` envelopes that stage already produces and validates, and never calls back into rule evaluation.

An action provider is a plain descriptor: `actionType`, a `requiredCapability` string (deliberately independent of `actionType`, so a future provider can gate on a stronger capability than its own name), `validatePayload(payload)`, an optional `authorize(payload, context)`, and `execute(payload, context)`.

Execution is a fixed pipeline, each stage failing closed with a specific structured code before any side effect can occur: request schema validity, provider registration (`UNSUPPORTED_ACTION_TYPE`), capability grant (`MISSING_CAPABILITY`), per-request authorization (`UNAUTHORIZED_ACTION`), payload validity (`INVALID_PAYLOAD`), then execution itself, with any provider exception caught and returned as `EXECUTION_FAILED` rather than thrown. `execute()`/`executeAll()` never throw for request-shaped input; every outcome - including a malformed request - is a schema-validated `ActionResult` (`src/actions/schemas/action-result.schema.json`).

Replay/duplicate handling is explicit: requests are keyed by `${correlationId}:${sequence}` (documented as unique within one evaluation run by the existing action-request schema). An identical replay of an already-executed request returns the original cached result with status `duplicate` and does not invoke the provider a second time. A different request that happens to reuse the same key is never conflated with the cached result - it is evaluated fresh on its own merits, since silently returning a stale result for a different action would be a correctness/security bug, not a convenience.

Two harmless local providers prove the architecture: `overlay.notification` (capability `overlay.notify`) and `system.log` (capability `system.log`), each delivering to an injected sink defaulting to a console line - no real I/O, network, emulator, or file access by default.

## Consequences

- Capability grants and provider registration are executor-construction-time decisions (e.g. one session's configuration), not something a rule or an action request can widen at execution time.
- A future, more dangerous action (memory writes, input injection, savestate control) plugs into the same four-stage pipeline by declaring its own `requiredCapability` and `authorize()` logic - the rule engine and the executor framework require no changes to represent it. Whether that capability is ever granted, and under what authorization, remains a decision for whoever constructs that future executor, not this contract.
- In-memory replay tracking is scoped to one executor instance's lifetime and is not bounded/expired - acceptable for this proof; a future task should address long-running-session growth if this executor becomes long-lived.
- This does not implement memory writes, input injection, savestate operations, webhooks, Discord/Twitch/OBS integrations, scripting, multiplayer, or provider-specific emulator actions. Those remain separate, later decisions requiring their own capability/authorization design.

## Addendum (focused fix round)

Independent review-readiness scrutiny found three gaps in the original replay/failure design, fixed on the same branch without changing the pipeline's stage order or `executeAll()`'s sequential contract:

1. **Concurrent duplicate execution.** The original design only guarded against a *sequential* replay (checking an `executed` cache before invoking the provider); two concurrent `execute()` calls for the same identity could each observe an empty cache and both invoke the provider. A second in-memory store, `inFlight` (a `Map<replayIdentity, Promise<ActionResult>>`), now closes this: the first caller for a given identity registers its pipeline promise in `inFlight` synchronously, before any `await` runs - JS's run-to-completion semantics guarantee no other call can interleave before that registration - and any concurrent caller for the same identity awaits that promise instead of independently invoking the provider. If the in-flight attempt succeeds, later callers receive a `duplicate` result; if it fails or is rejected, later callers receive that same non-success outcome, and the key is freed (via a `finally`) the moment the primary settles, so a failure can never deadlock or permanently poison the key - a subsequent identical call always gets a fresh attempt.
2. **Replay identity strengthening.** A bare `correlationId:sequence` pair identifies a request's declared *position*, not its *content* - two requests that legitimately differ (a different `ruleId`, a different `triggeringEvent`, a different `payload`) could previously be conflated if they collided on that pair. The chosen policy is a full canonical fingerprint: the replay identity is now a deterministic, object-key-order-independent serialization of `actionType`, `correlationId`, `sequence`, `ruleId`, `triggeringEvent`, and `payload` together. Two requests share a replay identity, for duplicate-detection purposes, if and only if all six match exactly; anything else is evaluated as an independent request on its own merits rather than either being silently treated as a duplicate or spuriously rejected as a conflict. (The alternative policy considered - reserving the bare `correlationId:sequence` key and returning a structured conflict result for any non-identical reuse - was rejected as unnecessarily strict: this platform has no guarantee that a caller replaying or rebuilding an event stream won't legitimately reuse that pair for unrelated content, e.g. in tests or a replayed correlation.)
3. **Contained provider/validator failures.** `execute()` must always return a schema-valid `ActionResult`, never throw, for any request-shaped input. Three previously-open gaps are now closed: (a) a provider returning a non-object value (a string, a number, an array) is detected explicitly and converted to a structured `EXECUTION_FAILED` result rather than being embedded verbatim into a result whose schema requires an object; (b) every place a caller-supplied hook (`authorize()`, `validatePayload()`, `execute()`) is invoked now normalizes a thrown value that is not an `Error` (`null`, `undefined`, a string, a plain object) via a `describeThrown()` helper, rather than reading `.message` on an untrusted value; (c) `buildResult()` itself now wraps its own `assertValidActionResult()` call in a try/catch and falls back to a minimal, guaranteed-schema-valid `INTERNAL_ERROR` failure result if an internally constructed result would otherwise fail its own schema - a defense-in-depth backstop, since (a) and (b) already close every known way that could be reached through the public API.

Executor-instance replay scope is unchanged and still worth restating: both `executed` and the new `inFlight` map are in-memory only, scoped to one `createActionExecutor(...)` call's lifetime, never persisted or shared across executor instances or process restarts, and `executed` still grows unbounded for the life of the executor - a future long-running-session task should still address bounding/expiring it, which remains out of scope for this proof.

## Addendum 2 (synchronous re-entrancy fix)

Item 1 above closed *asynchronous* concurrent duplicate execution, but a narrower gap remained: `const pipelinePromise = runPipeline(...); inFlight.set(key, pipelinePromise);` still calls `runPipeline()` (and lets it start running synchronously) *before* the reservation is recorded. `runPipeline()`'s synchronous prefix reaches a real suspension point (an `await`) only once it hits `provider.authorize(...)` - and only if the provider actually declares an `authorize()` hook. A provider with no `authorize()` hook runs `validatePayload()` and evaluates the `provider.execute(...)` call itself fully synchronously, with no `await` in between. If that provider's `execute()` is not `async` and calls back into `executor.execute()` with the identical request as its first statement, that re-entrant call happens *before* `inFlight.set(key, pipelinePromise)` ever runs in the original call, so it observes an empty `inFlight` entry and starts its own independent `runPipeline()` - which itself can immediately re-enter again, and so on, recursing until the stack is exhausted rather than single-flighting.

The fix defers the `runPipeline()` call itself to a microtask: `const pipelinePromise = Promise.resolve().then(() => runPipeline(validRequest, context, key)); inFlight.set(key, pipelinePromise);`. `Promise.resolve().then(callback)` schedules `callback` without ever running it synchronously - creating the promise and registering it in `inFlight` both complete in the *current* call's synchronous execution window, strictly before the queued microtask (and therefore before any part of `runPipeline()`, including a synchronously re-entrant provider) ever runs. Every other property from item 1 (concurrent-caller sharing, `finally`-guaranteed cleanup, no poisoning on failure) is preserved unchanged, since only the moment `runPipeline()` starts moved - not what it does or how its result is shared.
